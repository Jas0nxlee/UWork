# 周报 / 阶段汇报：主动汇报闭环（UWork skill 驱动）——方案（2026-10-18）

## 一、需求

**员工侧（现在就要做的）**：测试部的同事做完测试记录后，在 UWork 里**主动**跟 agent 说
"把我们本周的工作汇总分析一下，把内容和问题提出来" → agent 生成草稿、**本人确认** →
再说一句"发给部门领导" → 就发出去了。

**领导侧**：在 IM 里直接看到"某人同步过来了一份周报"，通知 + 未读 + 角标都是现成的。

**云端与留痕（必做）**：这些汇报要**保存在云端**并**有记录可查**（谁、哪个周期、什么内容、附件、
什么时候发的、谁看过了）——不是在本地磁盘上放一份文件。

**已明确推迟（2026-10-18 用户口径）**：从台账**自动/被动提取**产物并同步到"工作状态"，最后再做（见 §五），
现在不碰。

**现状（他们今天的做法）**：本地整理记录 → 导入多维表格 → 手填工作内容；汇报靠人工复制，领导靠翻表格。

## 二、这条闭环里我们已有的件

| 件                                     | 现状                                                                                           | 在闭环里的角色                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| UWork agent + office 三件套            | agent 能读写 Word/Excel/PPT，产出 .docx/.xlsx                                                  | 把"本周记录"整理成**一页纸**（内容/成果/问题）与附件                       |
| 技能（skill）机制 + **AIHub 技能市场** | 技能市场是**内置的公司技能来源**（受控、独立成段、不可删除，见 `specs/aihub-skill-source.md`） | **周报 skill 的分发渠道**：写一次，全部门在 UWork 里都能用，不需要改客户端 |
| IM（msgbus）                           | 单聊/群聊、未读/角标/系统通知/@提及/附件/检索/置顶/收藏，已上线并做过健壮性验证                | 投递与提醒：卡片消息 + 通知 + 未读；附件字节已在服务端卷上                 |
| 附件存储                               | msgbus 已有上传/下载 + 成员校验 + 卷                                                           | 周报附件（xlsx/docx/图片）直接复用，不另建存储                             |
| 目录（通讯录）                         | `/api/directory/users`（白名单内、对称可见）                                                   | 员工确认发送时**选收件人**（部门领导）                                     |
| 自动化/闲时任务                        | 产品已有                                                                                       | 后置：周几提醒交、未交催办                                                 |

**缺的那一块（关键路径）**：**agent 现在够不到 IM**（`IImService` 只被 UI/宿主使用）。
"让 agent 发出去"必须先补这个能力。三种落点，推荐先做①：

1. **核心能力端点（推荐）**：宿主暴露一个本机受限端点，只允许"以当前登录用户身份**提交一份汇报**"
   （像 `cua-permission-broker` 那样的能力代理）。**窄接口、可审计、不交出凭据**。
2. 核心内置 MCP 服务：把 IM 的 send/read/search 包成 MCP 工具（顺带把"agent 作为会话成员"推进一步），
   但要接进 agent 的 MCP 装配，改动面更大。
3. 直接给 agent 进程注入 IM 凭据：最省事，但把用户 JWT 交给了 agent 进程，**不推荐**。

## 三、要做的四件东西（按依赖排序）

### ① 周报 skill（人触发，包里带模板与脚本）

- 触发：用户在 UWork 里说"汇总本周工作"（或用技能名）。
- 素材来源（第一版）：**当前会话里已经发生的事** + 用户指的测试记录文件/目录 + 用户补充的几句；
  agent 归纳成三段——**本周做了什么 / 产出（附件清单）/ 遇到的问题**。
- 输出：对话里一份**可读草稿**（不是直接发出去）+ 可选生成一份 .docx/.xlsx 一页纸。
- 硬约束：**必须本人确认后才发送**；agent 不得自作主张发送。
- 分发：走 AIHub 技能市场（公司段），版本可迭代。

### ② agent 的"提交汇报"能力（缺的那一块，先补）

- 语义**不是**"随便发一条 IM 消息"，而是**"提交一份汇报"**：一次调用同时完成
  服务端落库 + 给收件人发一条卡片消息。这样"云端记录"与"IM 投递"天然是一件事。
- 入参：收件人（用户 id 列表）、周期（如 2026-W42）、标题、三段正文、附件（已有附件 id）。
- 出参：汇报编号 + 会话/消息 id，agent 据此回一句"已发送给 X（编号 R-2026W42-003）"。

### ③ 服务端"汇报"域（云端保存 + 记录）

- 表 `work_reports`：`id / org_id / author_id / department / period_key / title / summary / content /
problems / attachment_ids[] / status(submitted|reviewed|returned) / submitted_at / reviewed_by /
reviewed_at / message_id`。
- 端点：`POST /api/reports`（提交：落库 + 广播卡片消息）、`GET /api/reports?period=&author=&department=`
  （记录查询）、`POST /api/reports/:id/review`（领导回执：已阅/退回，可后置）。
- 消息侧：新增**受控 `kind='report'`**（只允许服务端产生，与 `system` 同一条规矩），
  body 是 `{reportId, periodKey, title, problems, attachmentIds}`；**长正文留在服务端**，卡片只放摘要。
- 权限：默认"作者本人 + 收件人（部门领导）+ 管理员"可见；跨部门不可见。
- 附件：复用现有上传接口与卷；报告撤回按留痕原则处理（只标记，正文仍可审计）。

### ④ 客户端：报告卡片 + "汇报"记录页

- 卡片渲染：`ImMessageRow` 增加 `kind='report'` 分支——标题 + 周期 + 三段摘要（问题单独一行高亮）+
  附件列表 + 状态徽标 + "查看详情"。
- 记录页：rail 现有 消息/通讯录/收藏，加第四项 **汇报**——按周期分组的列表（我发的 / 我收到的），
  可按人、按周期过滤；领导进来就是"本部门本周：8 人已交、1 人未交"。
- 导出：一键把某周期导出 .xlsx/.docx（复用 office 能力，可后置）。

## 四、工期与验收

| 阶段 | 内容                                                                                                                                        | 估时   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| P0   | **跨会话归集能力（§8.1，只读）** + ② agent 侧 im facade（宿主注入执行函数，照 browser-client）+ ③ 服务端最小域（提交/查询）+ 卡片 kind 渲染 | 3–4 天 |
| P1   | ① 周报 skill（含确认与发送） + ④ 记录页（我发的/我收到的）                                                                                  | 2 天   |
| P2   | 收件人自动带出（部门→经理映射）、未交提醒、回执、导出                                                                                       | 2–3 天 |

**P1 结束时的验收（可演示一整条）**：员工在 UWork 里说"汇总本周工作" → agent 给出三段草稿

双方都能在"汇报"页里按周期看到这条记录、附件可下载、服务端有落库。

## 五、后做：被动提取（用户已决定最后加）

2026-10-18 勘察到的现成台账：**taskjournal**（公司内网 HTTP MCP `192.168.20.100:3404`，有 task/artifact
（含 sha256）/evidence/关联/`timeline`（可按日周月聚合、按 agent 分泳道）/定时任务/语义检索；实测本周 374 条）。
它是**活动流水**，不是月度成果：大量 `(无标题)` + `artifacts:0`、`agent:"?"` 归属不明、混着 agent 中间轮次、
没有部门维度与经理映射。

所以那一期要补的是**六样**（不是再采集）：投递标记（deliverable）、归属（人+部门+项目）、可读化
（一句话标题/结论/问题，由模型基于产物与备注生成且要有事实锚点）、月度一页纸 + 问题清单、
经理映射与可见范围、投递渠道。并且要守住一条产品判断：**实时活动流不给领导看**（等于监控且噪声极大），
只把"提交动作"做成实时，成果按周期汇总；**员工必须能看到自己的台账与即将上报的内容**，并能标"不计入"。

## 六、边界与风险

1. **不做审批流**（收窄后的口径，见 §十四）：**不做通用审批引擎**（多级/分支/会签/超时升级）；
   但"这份该谁看、谁确认了"要做——路由 + 已阅/退回 + 留痕。不自建审批/考勤/日历这条既有结论不破例。
2. **发送必须人确认**（skill 硬约束）：agent 不能替人按下发送键；确认动作要留痕（谁、什么时候确认的）。
3. **权限默认最小**：报告只有作者、收件人、管理员可见；新域不要重复"反正只有一个组织"的假设。
4. **长文不进消息体**：卡片只放摘要，正文与附件在服务端；否则检索、列表、通知标题都会被长文本污染。
5. **同一周期允许重发**：按 (author, period_key) 保留最新一条为"当期"，历史版本可查（不做覆盖删除）。
6. **不要求员工两头填**：要留多维表格就做单向导入，不做双向同步。
7. **经理映射是后置项**：P1 让员工从通讯录里选收件人，不阻塞主流程；P2 再做"部门→经理"自动带出。

## 七、待拍板

1. 汇报的**周期口径**：自然周（周一~周日）还是他们的"实验周"？跨周补交怎么算？
2. **三段结构的固定字段**：本周做了 / 产出（附件）/ 遇到的问题——要不要再加"下周计划"？
3. **收件人**：只发部门经理，还是抄送组长/自己？P1 由员工选，P2 自动带出，是否需要"默认收件人"设置。

## 八、2026-10-18 修正（用户三点纠正后的定案）

### 8.1 素材来源：**本周所有会话**，不是当前会话（这一条把"归集能力"提到 P0）

用户口径：**"素材不可能只来自当前会话，它绝对是以本周所有会话中所做的相关工作内容为基础。"**

现状事实（本轮勘察）：

- agent **在自己的会话里看不到别的会话**——没有跨会话读取工具，所以现在的 skill 写出来只能"凭用户口述"，
  那不叫汇总。
- 底层其实有货：`packages/services/src/session/zcodeTaskService.ts` 的 `listTaskList()` 支持**跨任务全文检索**
  （`tasks-index.sqlite` 是真相源，返回 `searchable_text` + `snippets`），界面的 ⌘K（`TaskSearchDialog`）就走它。
  但它是**片段级**的，且**没有"按时间归集 + 展开全文"的能力**。
- 另有现成线索：taskjournal（内网 MCP `192.168.20.100:3404`）本周已有 374 条流水，含本地会话的工作内容——
  可当"本周做过哪些会话/任务"的索引来源，但语义不足（`(无标题)`、归属 `agent:"?"`）。

**定案**：新增一个**只读的"跨会话归集"能力**（宿主侧）：入参=时间范围（+可选人/项目），
出参=本周任务/会话清单（标题、时间、片段、产物路径、所属 workspace）。agent 用它拿到"骨架"，
再按需展开需要的会话全文。**它是 P0**（从 P1 提前），因为素材错了整条链就没意义。

### 8.2 agent 挂载 IM：**就在同一个软件里，不用绕外面**（推翻本文件 §三② 的"CLI + 环回"设想）

用户追问："同一个软件里不能直接去发送吗？还必须要走一遍外面吗？" —— **能，我原来的方案过度防御了。**

事实：App 里已经有一条"**agent 的工具由 App 侧执行**"的桥，先例就是浏览器：

- agent 侧有 `apps/zcode-cli/packages/core/src/browser-client/facade.ts`，它的关键签名是
  `BrowserExecuteFn = (command) => Promise<BrowserCommandResult>`——**执行函数是注入进来的**；
- 真正干活的是 App 侧（`packages/desktop/src/main/browserView/browserCommandExecutor.ts` 的
  `executeBrowserCommandOnView`）。也就是说：**浏览器明明活在 App 里，agent 照样能操作它**。
- 宿主本来就把 IM 注册进了服务通道（`packages/services/src/node.ts` 的 `.register(IImService, imService)`），
  令牌与连接全在宿主手里。

**定案**：照浏览器这条桥做——agent 侧加一个薄的 `im` facade（工具如 `im_submit_report` / `im_search`），
**执行函数由宿主注入**，工具调用落到宿主的 IImService，令牌不离开宿主、不新增网络面、不依赖 CLI。
CLI 子命令（`uwork im …`）保留为**可选的手**：给人工排障、批量脚本、以及"非 agent 场景"用，但**不是主路径**。

### 8.3 汇报不是"日报"：先定**承载形状**，后定字段与视图

用户口径：_"汇报的内容不应该只针对日报去设计……它相当于一个相对比较全面的云端存储，既可能包括文档，
也可能包括一些数据，或者其他形式。这部分我需要再调研分析一下大家的使用方式。"_

**定案**：数据模型改成**中性的工作记录对象**，日报/周报只是它的一种**视图**：

- 对象 `work_record`：归属（人/部门/项目）+ 时间与周期 + **类型标签**（实验记录/文档/数据/结论/问题/汇报…，
  可扩展）+ 标题 + 摘要 + 正文（或引用）+ **附件（任意形式：docx/xlsx/图片/数据集/链接）** +
  来源（会话 id / 任务 id / 外部链接）+ 状态 + 可见性 + 版本。
- 视图层（可后置、随调研调整）：按周期聚合 = 周报；按人 = 个人工作状态；按部门 = 领导视图；按类型 = 数据集/文档库。
- **先定承载形状的理由**：形状（对象 + 附件 + 版本 + 可见性）不受"大家怎么写"影响；字段与默认视图受影响。
  两条线**并行**，不互相阻塞。

**调研方案（低成本、可执行）**：① 3–5 人各 30 分钟访谈（现在怎么记、产出什么形态、谁会看、多久一次）；
② 采样他们现有多维表格的字段与若干行（脱敏）——这是最真实的"使用方式"；③ 让他们把最近两周产出按候选类型标签
分类，看覆盖率与未覆盖项；④ 我们侧观察（本周 taskjournal 374 条 + 本地任务）里"成果/噪声"的比例，
定默认视图的过滤规则。**时间盒 2–3 天，结论只影响标签体系与默认视图。**

### 8.4 前端先明确（用户要求：先定前端，再谈客户端实现）

三处前端形态（需要拍板的是交互与视野，不是实现）：

| 位置                  | 形态                                                                                                  | 待拍板                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 对话内                | 技能触发 → 段落式草稿（可改）→ 本人确认 → 发送回执（编号/收件人/时间）                                | 草稿是否强制配一份一页纸附件；是否允许"只发正文不发附件" |
| 记录页（rail 第四项） | 默认视图 = 本周期：我提交的 / 我收到的；筛周期、人、类型；每行 = 标题 + 摘要 + 附件 + 状态 + 来源会话 | 默认视野（只本人 + 领导，还是组内互看）；要不要"草稿箱"  |
| 接收侧（领导）        | 消息卡片（标题 + 摘要 + 附件 + 展开）+ 系统通知 + 未读角标；默认按"人 × 周期"分组                     | 卡片上要不要"已阅/退回"按钮；未交名单要不要显示          |

### 8.5 汇报的"形式"：它是**协作 + 文案**，不是上报表单

用户口径：_"汇报只是一种工作内容，它本质上还是要解决协作的问题，也就是一个文案写作的问题。我们应该如何考虑它的形式？"_

**这个提炼是对的，而且它直接否掉"表单单条"的思路。** 四种候选形式的取舍：

| 形式                                 | 适合                                 | 致命点                                                                             |
| ------------------------------------ | ------------------------------------ | ---------------------------------------------------------------------------------- |
| 纯消息（长文本发进 IM）              | 一句话进度                           | 不能评论/修订/引用，第二周就找不回来，聚合难                                       |
| 表单单条（字段一条条填）             | **数据型**（测试结果、指标、样本量） | 叙事型内容（做了什么/为什么/卡在哪）塞进字段就变形，也是他们今天在多维表格里的痛点 |
| **文档 + 元数据 + 协作面（选这个）** | 汇报这种"叙事 + 协作"的东西          | 需要定"一事一份还是一周一份"（见下）                                               |
| 实时协同编辑（飞书文档那种）         | 多人同时改同一份                     | **明确不做**：那是另一个量级的产品；第一版做"读写分离 + 版本快照 + 评论"           |

**所以"形式"分三层，各有各的落点**：

1. **写（文案）**：正文是**文档**——agent 用现成的 office 能力起草/修订（这正是"文案写作问题"），人改；
   元数据只是挂在它外面的壳：归属（人/部门/项目）、周期、**类型标签**、来源（本周哪些会话/任务）、可见性、状态。
2. **协作（本质）**：**评论**（针对段落或整体）+ **@提及**（IM 已有）+ **版本与留痕**（谁改了什么）+
   **已读回执**（领导看过没有——这是协作闭环的标志）+ **引用**（下期引用上期结论、汇总引用多条产出）。
   评论挂在**文档**上，不挂在 IM 消息上；但**通知**走 IM（"有人评论了你的汇报"）。
3. **聚合（视图）**：周报 / 月报 / 个人工作状态 / 部门视图，都是同一批文档的**视图**（按周期、按人、按事聚合）。
   **"一页纸"是视图（让领导 30 秒看懂），不是载体**；正文永远在文档里。

**三个会影响形态的判断**：

- **一事一份，还是一周一份？** 协作的真实对象是"事"（一份实验记录、一个测试结论），周报只是视图。
  若强行按周一份，评论与修订会**跨周断裂**（下周一没人知道上周那条评论说的是哪份数据）。
- **评论挂哪儿**：挂文档。挂聊天里 = 讨论散落，第二周找不回来；但**IM 负责通知**。
- **最短动作优先**：目标是协作，那么"**领导能一句话回**"比"报告更漂亮"重要——卡片上直接给
  「已阅 / 回复评论 / 退回」三个最短动作，比让人打开一个门户再找输入框强得多。

### 8.6 交互定稿（用户 2026-10-18 描述）：两个素材入口 → 一张汇报卡片 → 汇报 / 暂存

用户口径（原话）：素材来源两种——① **材料由 Agent 协作产生**；② **用户在 Office 里手动填好**后告知 agent，
方式有两种：**(a) 提供当天的文件**、**(b) 直接拖到 UWork 里**。agent 收到材料后直接阅读并分析，
生成**一张需要汇报的卡片**；用户可选 **"汇报"（直接发出去）** 或 **"暂存"（保存在本地）**。

**现成能力核对（都已确认）**：

| 环节                 | 现状                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ②-（a）给文件/给路径 | agent 本来就能读工作区文件（office 三件套读取能力已在）                                                                                                                                                  |
| ②-（b）拖进 UWork    | **主对话输入框已支持**：`packages/ui/src/components/ai-elements/prompt-input.tsx` 监听 `dragover`/`drop` 并 `add(dataTransfer.files)`；**IM 输入框还不支持拖拽**（只有 file input），要补一个小 `onDrop` |
| ① agent 协作产物     | 会话内的产物本来就在工作区/附件里，agent 自己有路径                                                                                                                                                      |
| 卡片上的两个动作     | 现成机制是**提问式交互**（`packages/ui/src/ElicitationDialog.tsx`）：agent 出草稿 + 问"汇报还是暂存"，用户点一下即可，**第一版不用新做 UI**                                                              |
| 汇报（提交）         | 走 §三②：宿主注入的 im facade → 服务端落库 + IM 卡片投递                                                                                                                                                 |
| 暂存                 | 见下面的三个提醒                                                                                                                                                                                         |

**卡片上必须有什么**（让人在 10 秒内判断"该不该发"）：周期、**报给谁**、三段摘要（做了什么 / 产出 / 问题）、
附件清单（名字 + 大小）、以及**素材来源清单**（本次读了哪些会话、哪些文件）。

> "素材来源"这一项不是装饰：**没有它，人无法核对 agent 有没有漏掉或编造**。这与 §五"事实锚点"是同一条原则。
> 它同时也是 agent 自己的护栏——要列出处，就不能凭空写。

**"暂存"的三个提醒**：

1. **暂存落成工作区里的文件，而不是应用私有状态**：建议 `<工作区>/工作汇报/<周期>.md`（或 .docx），
   这样它天然可被 agent 再读、再改、再汇报，用户自己也找得到；记录页的"草稿箱"只是它的索引视图。
2. **本机暂存 = 多设备看不见**：换机器就没了。第一版可以接受（草稿本就是私货），但要在界面上说清"暂存只在
   这台机器上"；要跨设备就得做成云草稿（可后置）。
3. **暂存后要能"改完再发"**：草稿 → 再编辑 → 再汇报，是这条链的常见路径，别把暂存做成单向的"存档"。

**建议的实现顺序**：P0 用提问式交互跑通"草稿 → 汇报 / 暂存"（零新 UI）；P1 再做**原生卡片组件**
（与 IM 侧的报告卡片共用一套渲染）。

### 8.6.1 agent 端卡片：沙箱渲染 + 真按钮（2026-10-19 落地，同日补上按钮）

用户问"agent 端的卡片渲染呢"——这是原始交互设计（§8.6）里唯一没落地的一环。落地方案与**它做不到什么**：

**做法（客户端零改动）**：技能包新增 `card.template.html`（卡片：标题/周期/三段摘要/问题高亮（红左条）/字段网格/
附件行/**底部「汇报 / 暂存」按钮**，颜色只用沙箱设计令牌，明暗主题自动跟随）与 `scripts/render-card.mjs`
（草稿 → HTML + 一行 `::visualize{"path":"…"}` 指令）。
agent 生成卡片、**把那行指令原样贴进回复**，应用就把它渲染成对话里的内联卡片——走的是产品已有的 Gen UI 沙箱。

**三条硬约束（错了就是"卡片静默地不出现"，真机踩过一遍）**——以后凡让 agent 生成可视化的技能都适用：

1. **文件必须落在宿主输出根目录内**：`readGenUiDocument` 只放行 `${ZCODE_GEN_UI_OUTPUT_ROOT}/**`
   （即 `<数据根>/visualizations`），写 `/tmp` 或工作区会在渲染时被拒。宿主已把该变量注入 agent 进程
   （`zcodeAgentProcessManager`），所以脚本自己就能找到目录——`render-card.mjs` 因此**默认不接受外界挑路径**，
   `--out` 只在显式给出且过校验时用。文件名还须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*\.html$`（大写/下划线/点开头都不行）。
2. **内容必须是 HTML 片段**：沙箱 `assertGenUiFragment` 拒绝 `doctype/html/head/body` 标签（它会把片段塞进自己的
   `<body>`）。模板写成整篇文档要到渲染时才炸，所以脚本生成时先自查一次。
3. **指令必须是正文纯文本**：`gen-ui/domain/references.ts` 用 `findMarkdownCodeRanges` 排除 markdown 代码区，
   ```代码块 /`行内代码`/`<pre>`里的`::visualize` 一律**保持惰性**（防"示例被当指令"）。
   agent 很容易"为了排版好看"把它包进代码块——SKILL.md 里因此写成硬规则。

**真机验证（2026-10-19）**：dev 实例里让 agent 跑 `render-card.mjs --draft /tmp/qa-chain.json`（不传 `--out`）→
卡片落进 `~/.uwork/v2/visualizations/card-<时间戳>.html` → agent 贴出指令 → 对话里出现内联卡片
（`[data-testid="gen-ui-card"]`、`data-gen-ui-phase="ready"`），字段网格/周期芯片/页脚提示均正常。
踩坑记录：第一轮卡片写到 `/tmp` 且指令被包进 ```text 代码块——两条都命中，卡片一次都没出现，且**没有任何报错**。

**版式口径（用户 2026-10-19 两轮反馈：先"贴左别扭"、再"没撑满，要自适应"）**：定为**撑满正文列**——
`width:100%`，**不设 `max-width`、不居中**。依据就在客户端代码里：`GenUiCard` 的注释写着
「会话父容器已经负责宽度；卡片再次限宽会让 inline UI 无法填满正文」，所以卡片自己限宽是**反例**。
卡片内部随宽度自适应：台账字段用 `grid-template-columns: repeat(auto-fit, minmax(180px, 1fr))`，
宽屏 5 列、窄列 3 列，不会撑满后每格右侧留一大片空。

**尺寸变化的自适应是现成的，但要用真布局变化去验**（2026-10-19 实测，关闭/打开右侧边栏）：

| 状态       | 会话列 | 沙箱 guest 视口 | 卡片宽 | 字段列数 | 内容高 | 宿主锚点高            |
| ---------- | ------ | --------------- | ------ | -------- | ------ | --------------------- |
| 右面板关闭 | 1094   | 1104×338        | 1094   | 5        | 338    | 338px                 |
| 右面板打开 | 788    | 798×386         | 788    | 3        | 385    | **386px（自动跟随）** |

链路是：宿主锚点宽度由 CSS 决定（`w-full`）→ `webview` 随之 `width:100%` → guest 重排 →
`genUi.ts` 的 `ResizeObserver`/`resize` 量到新内容高 → `sendSizeChanged` → `page.ts` 的
`onsizechange` 写回 `snapshot.height` → `PageAnchor` 改高度。页脚底 380 ≤ 内容高 385，**无裁切**。

踩坑（验自适应时别再用错工具）：`Emulation.setDeviceMetricsOverride` 会把**沙箱 guest 自己的视口**一起改掉
（guest `innerWidth` 变成 1000，而它的宿主盒子只有 688），于是出现"卡片被整体缩小、字号变小"的假象。
验窗口/面板引起的尺寸变化，要用**真实布局变化**（折叠侧栏、开关右侧面板、真实 window resize）。

这两条版式调整只改技能包里的模板，**不动客户端、不用重启应用**。

**卡片上的按钮（2026-10-19 补上，原先判断为"做不到"是错的）**：当时的结论是"沙箱只读、按钮发不了消息"，
所以"汇报/暂存"只能靠用户**回一句话**。查代码后发现沙箱运行时**本来就暴露了 follow-up**
（`window.zcode.sendFollowUpMessage`，MCP Apps 的 `sendFollowUpMessage` + 宿主 `consumeUserGesture` 手势校验），
只是我上一轮没核对就下了结论。现在卡片底部就是**两个真按钮**：

- 点「汇报」/「暂存」＝ 用户替自己说那句话，提示词形如 **`汇报：<标题>`** / **`暂存：<标题>`**
  （带标题是为了同一个人手里有多份草稿时不混淆），走 follow-up 进会话，agent 按 SKILL 的同一套词识别。
- **脚本不可能自己触发 agent**：宿主对 follow-up 强制校验用户手势，没手势就退化成一次确认弹窗
  （实测合成点击就是这条路径：弹窗里预填着 `暂存：agent 链路验证 03:30:08`，点「发送」才进会话）。
  这把"卡片能带按钮"从"有风险"变成"结构上安全"。
- **提交仍然是 agent 的事**：按钮只负责把话带回去，SKILL 里写明"两者都**不等于**已经提交"。
- 环境里没有 `window.zcode`（比如把这张 HTML 拿到浏览器里直接看）时，按钮不静默失败，
  而是提示"直接回一句「汇报：…」就行"。

**「暂存」必须是纯本地（用户 2026-10-19 纠正）**：用户口径是"暂存不发送，只在本地留存"。第一版把两个按钮
都做成了 follow-up——**即使没有落到台账，点「暂存」仍然会往会话里发一条消息、唤起一轮 agent 与模型请求**，
这跟"只留本地"不是一回事。现在两件事分开：

- **「汇报」= follow-up**（要 agent 去做事：提交）。这是唯一会让 agent 动起来的按钮。
- **「暂存」= 纯本地**：不发消息、不进会话、不打模型，只把 `stagedAt` 写进 Gen UI widget state 的
  **`privateContent`**（`modelContent` 是随上下文带给模型的那半边——写错这半边就等于把"本地标记"泄给了模型），
  落在本机 `~/.uwork/v2/gen-ui-state/<scope>/<path>.json`。草稿文件本来就在本机（卡片上那行
  「草稿在本机：<路径>」就是它），暂存不需要任何其它动作。卡片重渲染时读回本地状态显示「已暂存（本机）」。

实测（真机）：点「暂存」→ 无确认弹窗、agent 未被唤起、**会话内容一字未变**、台账无新增记录；
本地状态文件是 `{"modelContent":null,"privateContent":{"stagedAt":"2026-10-19T08:42:33.074Z"}}`。
回归测试：`packages/ui/test/agentReportCardActions.test.ts`（7 条，含"暂存**一条消息都不发**"与
"只写 privateContent"两条硬断言）。

**真机验证（2026-10-19）**：agent 现生成卡片 → 底部出现「汇报 / 暂存」→ 真点「暂存」→ 宿主确认弹窗
（预填正确提示词）→ 发送 → 会话里出现 `暂存：agent 链路验证 03:30:08` → **agent 正确识别为暂存**
（记成 staged、`submitted: false`，并回"下次回「汇报：…」我接着走提交"）。
「汇报」那条弹窗里同样预填了 `汇报：agent 链路验证 03:30:08`（为不给部门负责人添验证记录，未发送）。

**暂存的东西要能被找回来：抽成平台通用件「本地暂存箱」（2026-10-19 用户提出）**

用户口径：_"这个 skill 应该能够去获取它暂存的这个……这个只是针对特殊业务场景，它有没有一些通用的方式"_。
当时的缺口是两个：① 卡片上的「暂存」标记写在 Gen UI 的 widget state 里，**只有那张卡片看得见，agent 读不到**；
② 草稿放哪由各 skill 自己决定（`/tmp`、工作区随手一个文件名），"我上周暂存的那份呢"没人答得上来。

定案：**暂存＝文件已经在暂存箱里**，跟具体业务无关，抽到 `skills/_platform/drafts.mjs`（契约见
`skills/_platform/LOCAL-DRAFTS.md`）：

- 位置：`UWORK_DRAFTS_DIR` → `<ZCODE_STORAGE_DIR>/drafts` → `~/.uwork/drafts`（**用户级**，换项目/换会话都还在，
  也不污染 git 仓库）；一条草稿一个目录 `<root>/<id>/{draft.json,payload.json}`。
- 编号：`yyyymmdd-hhmmss-<类型尾段>`；**同一秒撞号要顺延**（实现时真踩到：撞号会静默覆盖前一份草稿）。
- 状态只有三态：`staged` / `submitted`（带业务编号）/ `dropped`；`prune` 只清 `dropped`
  ——**没报出去的东西不能被悄悄删掉**。
- **平台不解释 `payload.json`**：字段、模板校验、审核人路由都是各业务自己的事，所以新增业务不用改平台。
- 找回：`drafts.mjs list`（默认只列还没报出去的，输出是人话，agent 直接照读）。

接线：SKILL 第 1 步＝汇总完**立刻 stage**（草稿一写出来就入箱，用户点不点卡片上的「暂存」都无所谓）；
`submit-work-item.mjs --draft-id <编号>` 在**提交成功后**把那条标成已报出（失败则保持 staged，不会"假装报过了"）；
`render-card.mjs --draft-id` 把编号写到卡片上。测试：`packages/ui/test/platformDrafts.test.ts`（7 条，
含"提交被拒 → 草稿仍留在待办"与"路径穿越/非法编号一律拒"）。

**为什么没改成"原生卡片"**：原生（把 `ImCardDocument` 投影进会话正文）的额外收益只有"视觉/架构与 IM 侧统一"
和"客户端直接执行 `server` 动作"；而汇报这条链的动作语义是"**把话交给 agent**"（草稿在 agent 手里，
提交是 agent 执行的），follow-up 正好是这个语义，原生卡片在这里换不来新能力、却要动消息投影那条被仔细测过的路径。
**触发条件**（满足任一条再上原生卡片）：① 会话里的卡片需要客户端**直接**改服务端状态（小载荷，如"已阅/退回"）；
② 需要卡片在刷新/换设备后**一模一样**地复现（HTML 文件路径那套约束太多）；③ 视觉上要求与 IM 卡片逐像素一致。

#### 8.6.1 拖入（已落地，2026-10-18）

用户口径："我说的拖拽文件就是拖到和 Agent 的会话里，但是 IM 的输入框应该也支持拖入才行。这两方面都要做到。"

- **会话侧（agent 对话）**：本来就实现了——`v4/ConversationComposer` 的 `handleConversationDrop` +
  `usePromptEditorDragState({ enableExternalFileDrop, enableWorkspaceFileDrop })`；OS 文件走上传队列，
  从**文件树**拖入则插入 mention（不上传，语义不同）。本轮真机复核：拖入文件后输入区出现附件名与"移除附件"。
- **IM 侧**：本轮补齐。`ImComposer` 现在是三个处理函数——`onDragOver` 只认 `types` 含 `Files` 的拖拽
  （拖选中的文字经过不会亮）、`onDragLeave` 用 `currentTarget.contains(relatedTarget)` 判真离开
  （拖过子元素会连发 dragleave）、`onDrop` 走**已有的** `onFiles` 上传发送路径；拖入时给一条
  「松开即发送文件」提示（`data-testid="im-drop-hint"`）。
- **真机实测**：IM 输入框上派发带 `File` 的 drop → 39 B 文件上传成功、作为附件消息入库
  （`kind='attachment'` + attachmentId/name/mime/size），时间线显示"拖入验证-实验记录.txt | 39 B"；
  dragover 出提示、dragleave 收起。**注意口径**：CDP 造不出 OS 级拖拽手势，这里验的是"drop 事件带文件之后
  会发生什么"（与真实拖拽走同一个事件与同一份 `dataTransfer.files`；会话侧生产早就在用这条机制）。
- **回归测试**：`packages/ui/test/imComposerDrop.test.ts`（4 条：拖入走发送路径并把文件交出去、
  拖入出提示松手收起、拖文本不点亮也不外发、文件树载荷不假装成功）。
- **后置**：从**文件树**拖入 IM 需要"按路径读字节"的宿主能力（渲染层现在读不到），本轮不做，
  宁可什么都不发生也不做假成功；等做"汇报卡片/记录页"时一起加。

### 8.7 卡片必须是**通用架构**，不是一个功能写一个（用户 2026-10-18 纠正）

用户口径：_"我觉得你的实现有点太机械了，你完全写死了。正常情况下，这种类似的卡片选择，不应该是一个通用架构，
而是基于某些动态文件渲染自动生成一个卡片吗？"_ —— **成立，而且我不该那么写。**

把「汇报」做成一个专用 `kind='report'` + 一个专用卡片组件 + 一个专用弹窗，后果不是"丑"，是**每加一种卡片
（测试结果卡、数据集卡、审批请求卡、周报以外的阶段成果卡）都要发一次客户端版本**——而我们的分发链路本来
就是当前最大的卡点（没有安装包、没有更新通道）。这种写法的成本会一直往上涨。

#### 仓库里已有的两套"通用渲染"（别再造第四套）

| 机制                                                           | 现状                                                                                                                                                              | 能否用在 IM 卡片上                                                                                                                                                                                    |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Gen UI 沙箱**（`packages/ui/src/gen-ui/`，有 `CONTRACT.md`） | 助手消息用 `::visualize{path=...}` 引用一个 HTML 文件，应用渲染成**受限沙箱页**（初始 240px、上限 10000px、无工具、只读绑定、外链走 `ui/open-link` 且要原生手势） | **技术上可以，但信任模型不对**：它服务的是"你自己的助手 + 你本机的文件"（同一信任域）。IM 卡片来自**别人**，HTML 内容是攻击面（钓鱼页面、伪造的"重新登录"、假附件），沙箱挡得住脚本、挡不住**骗人**。 |
| **MCP Apps**（`@zcode/shared/mcp-apps`）                       | MCP 服务可以自带 UI 页面                                                                                                                                          | 同样是"可信提供方"模型，不适合任意成员发来的消息                                                                                                                                                      |

#### 定案：**声明式卡片文档 + 一个通用渲染器 + 服务端校验的 action 通道**

这就是成熟 IM 的做法（Slack Block Kit、Teams Adaptive Cards、飞书消息卡片都是这个形状），也是"基于动态文件
生成卡片"的安全版本：**卡片是数据，不是代码；加一种卡片 = 加一份文档/模板，不发客户端版本。**

- **一个消息 kind 就够**：`kind='card'`（把现在的 `report` 收进去当第一个 `type`）；
  卡片类型与版本写在文档里（`{ card: { version, type } }`），客户端不再按 type 分支写组件。
- **文档结构（原语集合刻意很小）**：`title / subtitle / badges / sections[ text | fields | list | quote | divider |
progress | table ] / attachments / actions`。原语小是这个架构能成立的原因——一旦允许任意布局，就等于
  在消息里写前端。
- **`fallback` 必填**（服务端拒绝没有 fallback 的卡片）：会话列表预览、系统通知、全文检索、企微兜底消息、
  以及"客户端不认识这个 type/version"时，全都退化成这段纯文本——**永远不出现空白卡片或读不出来的 JSON**。
- **未知字段忽略、未知 section 跳过** → 前向兼容：服务端先上新 section，老客户端照旧能用。
- **actions 分两种**，都不含代码：`kind:"client"`（打开一个界面，例如"查看详情"，由客户端注册的 target 处理）、
  `kind:"server"`（POST 到服务端 action 端点，**服务端校验"这个人能不能对这个卡片做这个动作"**，再走注册的
  处理器，返回更新后的卡片）。按钮的权限判定**永远在服务端**，不信卡片自己的声明。
- **模板以数据形式分发**（报告/测试结果/数据集/请求… JSON schema + 样例），走 AIHub 技能市场跟 skill 一起发；
  作者（通常是 agent）按模板填数据，渲染器不需要认识这个模板。

#### 与现有实现的关系（迁移成本≈0，现在正是时候）

当前那套 `kind='report'` + `ImReportCard` + 弹窗**还没有发给任何用户**（没有安装包、没有分发），所以现在
改形状几乎零成本——这正是"先把它做通用"的最佳时机。迁移动作：

1. 服务端：`work_reports` 表**不动**（它是记录域，与呈现解耦是正确的）；只把发出的那条消息的 body 从
   `{reportId,title,problems,...}` 换成**卡片文档**（含 `fallback` 与 `actions:[{id:"open"}]`）。
2. 客户端：`ImReportCard` 退化成"第一个模板"或直接删掉，改由**通用 `ImCardRenderer`** 按文档渲染；
   详情弹窗保留（它是 `action id="open"` 的客户端处理器，与卡片形状无关）。
3. 协议：`kind` 枚举里 `report` 换成 `card`；`parseImReportMessage` 换成**卡片文档 schema 校验**
   （校验失败 → 用 `fallback` 文本，绝不抛给用户一段 JSON）。

#### 边界（避免这套东西失控）

- **不许任意 HTML/JS 进 IM 卡片**（Gen UI 沙箱留给"本地助手 + 本机文件"那一侧）；
  真需要富交互时，走"可信提供方"（本地助手或服务端模板），且仍然只有受限 bridge。
- **渲染器只认原语**：遇到不认识的 section 忽略并记一条日志，不要 attempt 渲染未知结构。
- **卡片不是正文的替代**：正文仍然留在服务端（`work_reports`），卡片是"入口 + 摘要"。

#### 8.7.1 已落地（2026-10-19）

**协议**（`packages/shared/src/imCard.ts`，`im.ts` 再导出）：`ImCardDocument` + `parseImCard`。
校验规则就是上面的三条硬规矩——**缺 `fallback`、缺 `card.type`、缺 `version`、坏 JSON 一律判无效**；
不认识的 section 丢掉、`kind` 不是 client/server 的 action 丢掉（"跳过"而不是"渲染未知结构"）。
`kind` 枚举里 `report` 换成 `card`（`ImMessageKind = text | attachment | system | card`）。

**服务端**：`work_reports` 表与端点**没动**（记录域与呈现解耦的正确性在这里体现）；只把投递的那条消息
从"汇报专用载荷"改成**卡片文档**（`appendReportMessage` → `appendCardMessage`，`kind='card'`）：
title/period/三段 sections/问题徽标/附件元数据/`actions:[{id:"open",kind:"client",target:"reports.work_report:<id>"}]`，
`fallback` 形如 `[汇报] 2026-W42 标题 · 做了什么… · 问题：… · 附件 N 个`。生产已部署；
库里那条历史 `kind='report'` 消息用一段 SQL 按其记录行重建成了卡片文档（**没有留旧格式的兼容分支**）。

**客户端**：`ImCardRenderer` 替换原来的 `ImReportCard`（后者已删）。渲染器按原语渲染
（text/fields/list/quote/divider/progress + badges + attachments + actions），
`data-card-type/-version/-action` 挂在 DOM 上便于断言；解析失败退化成提示文本。
`client` 动作交给外层（面板按 `target` 的 `类型:标识` 找处理器，`open` → 详情弹窗拉服务端记录）。

**真机实测**（dev 实例 + 生产 msgbus）：卡片按文档渲染（type/version/徽标/动作/三段文本都对）；
会话行预览显示 **fallback**；点"查看详情"拉到服务端记录并展示；
从界面"汇报页 → 写汇报 → 汇报"提交后：云端落库（`2026-W43` 周期正确按 ISO 周算）、
收件人视角 `GET /api/reports` 能看到、会话里最后一条消息就是卡片文档（seq 281）。

**回归测试**：`packages/ui/test/imCardRenderer.test.ts`（7 条：按原语渲染、client 动作回调、
**未知 section 跳过**、**未知 type/version 仍渲染**、**缺 fallback/缺 type/坏 JSON 退化成提示**、
解析器丢掉认不出的 section 与 action kind）+ 服务端 `workReports.test.ts` 断言卡片文档形状
（`card/fallback/badges/sections/actions`）。IM 相关 128 条、服务端 98 条全绿。

**这一轮抓到的两个真 bug（都属"载荷泄漏"同一类）**：

1. **会话列表预览把卡片 JSON 当正文**：预览分支只认 system/attachment，卡片走到默认分支显示原始 JSON。
   修法：新增 `kind === "card"` 分支用 `parseImCard(body)?.fallback`。
2. **系统通知会弹出 `{"card":...}`**：通知 body 对非附件消息直接 `message.body.slice(0,120)`。

   （system / attachment / card 三种载荷），新增一种载荷就要把这三处（预览、通知、检索）一起过一遍。

**视觉（2026-10-19 补，用户："有点简陋"）**：架构对了不等于好看——第一版卡片是"一块灰底 + 一列同色文字"，
标题与正文只差字号、label 与内容混成流水账、问题只是把字染红、动作按钮孤零零一个。返工方式沿用本仓库
在 IM 上验过的那套：**先拿像素再改**（CDP `Page.captureScreenshot` + `clip` 截卡片区域，改一轮看一轮）。

落地：新增 `packages/ui/src/im/imCardChrome.ts` 作为**通用卡片的视觉系统**（与卡片类型无关）——
结构固定为「类型图标 + 标题 + 元信息行 → 分区 → 附件行 → 底部动作条（右对齐、有主次）」，
颜色只由 tone 决定：左侧 2px 强调条（有危险段取危险色，否则取徽标色）、徽标胶囊（warning 琥珀 / danger 红 / success 绿）、
问题块用「底色 + 左描边 + 图标」（**只染红字看起来像程序报错**，不像"内容里有个坎"）、
附件一行一个（图标 + 名字 + 大小，不塞成一片小芯片）、动作条与内容用分隔线断开且主按钮实心。
写汇报弹窗与汇报列表同步重做（头部图标 + 周期 chip、字段带 label、三段按卡片上的顺序排、
底部「暂存（ghost）／汇报（primary）」；列表行加状态与"有问题"胶囊）。

**仍然没做**：写汇报弹窗**还不能加附件**（附件要先传到与收件人的单聊里再提交——这条路径服务端已支持，
弹窗里缺一个文件选择器）；`kind:"server"` 动作与卡片模板分发同前一条。

**仍未做（下一步）**：`kind:"server"` 动作的服务端执行与校验（现在渲染器会画出来但不执行）——
需要 msgbus 加 action 端点 + `(card.type, action.id)` 的处理器注册表，权限判定在服务端；
以及"卡片模板以数据分发"（先把模板 JSON/schema 放进 AIHub 技能市场随 skill 一起发）。

## 九、真实台账勘察：`2026年测试与服务保障部工作表.xlsx`（2026-10-19，用户提供）

这是他们**现在实际在用的汇总单**。读完全部五个工作表后，结论是：**粒度、周期、字段、收件人、词表
都和我原来的假设有出入**——这些出入比功能本身重要，逐条记下来。

### 9.1 它是什么（五个表，同一套骨架）

| 工作表                        | 规模                      | 一行是什么                                                         |
| ----------------------------- | ------------------------- | ------------------------------------------------------------------ |
| 01-2026年测试情况统计表       | **725 行 × 23 列**，15 人 | 一个项目在**某一个月**的测试情况（同一项目 2/3/4/5/6 月各一行）    |
| 02-2026年配置项测试情况统计表 | **只有表头**（24 列）     | 配置项级度量：版本个数 / 评审总次数 / 评审通过次数（还没用起来）   |
| 03-2026年测试问题汇总表       | **445 行 × 19 列**        | 一条测试问题（描述/分类/级别/是否关闭/原因分析/解决措施/关闭日期） |
| 04-2026年售后工作统计表       | 36 行 × 19 列             | 一次售后动作（内容分类/是否保内/时效）                             |
| 05-2026年其他工作统计表       | 192 行 × 14 列            | 一件其他工作（保密管理/信息化运维…）                               |

**五个表共用的骨架**（这就是真实的"工作记录 schema"）：

1. **归属**：项目编号 / 项目名称 / 项目状态 / 所属部门 / **项目经理** / 工程师
2. **对象**：产品（名称、数量）/ 配置项（编号、名称、软件等级）
3. **时间**：开始日期 / 结束日期
4. **分类（受控词表）**：测试内容分类（`5-编制配置项测试计划`、`14-系统联试/联调`、`16-其他测试`）、
   测试方式（**`AI测试` / `传统测试`**）、问题分类（软件/元器件）、问题级别（`1级-严重`…`5级-需改进`）、
   售后内容分类（`1-安装调试`/`3-任务保障`/`4-技术咨询`）、其他工作分类（保密管理/信息化运维）
5. **内容**：简述被测对象版本编号 / 简述测试内容 / **工作输出物**（逐行手填的产物名）
6. **问题**：01 表内嵌一列"发现问题及解决情况"，03 表独立成表
7. **度量**：测试数量、版本个数、评审次数/通过次数、售后时效、是否保内
8. **审计**：**创建人 / 创建时间 / 最后编辑人 / 最后编辑时间**（五个表都有）
9. **是否统计**：01 表第 18 列——他们已经有一个"这条不计入统计"的开关

### 9.2 这些发现改变了什么

| 原假设               | 真实情况                                                                                                         | 影响                                                                                                |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 汇报周期 = 周        | **主单位是"月"**（每个项目每月一行；周在数据里不存在）                                                           | 主视图改成「**项目 × 月**」；卡片 `periodKey` 用 `2026-10` 这类月键，周报只是可选视图               |
| 收件人 = 部门经理    | **项目经理往往跨部门**（载荷控制部/卫星能源部/箭载综电部/机载综电部/整机平台部/深蓝智航部…）——测试部是**服务方** | 验证了"P1 让员工选收件人"是对的；且默认收件人应**从记录里带出项目经理**，不是本部门领导             |
| 一段正文 + 问题      | 每行有 8-10 个结构化字段                                                                                         | **不用改协议**：`fields` 原语正好装键值对、`list` 装工作输出物、`text` 装简述——通用卡片这条路走对了 |
| `tags` 自由文本      | **全是带编号的受控词表**（`5-`/`14-`/`3级-`/`1-`）                                                               | 词表要成为**一等输入**：部门维护一份词表 JSON，随技能市场分发；agent 只能从词表里选，服务端校验取值 |
| 留痕是我们的坚持     | 五个表本来就有**创建人/时间、最后编辑人/时间**                                                                   | 留痕要**对齐这四个字段**（不是加点什么，是别少给）                                                  |
| "不计入"是我们的设计 | 他们已有"是否统计"列                                                                                             | 直接沿用这个语义做开关                                                                              |
| 交付物要另建模型     | **"工作输出物"就是逐行手填的产物名**，而这些产物本来就产在 UWork 里                                              | "被动提取"那一期的落点明确了：从工作区认出交付物 → 预填这一列                                       |

**另外两个值得注意的点**：

- **`测试方式 = AI测试`** 已经出现在真实数据里 —— 部门在统计"这次是不是用 AI 做的"。AI 参与度是他们的指标，
  而 UWork 自己就知道这件事，**不需要人再填**（这是最容易被自动化的字段）。
- **02 表是空的**（只有表头）：配置项级的"版本个数/评审总次数/评审通过次数"设计了口径但**没人手填**。
  这是最好的切入点——这些数在 UWork 里做配置项测试时是现成的，**我们能替他们把这张表填起来**，
  而不是先要求他们改变习惯。

### 9.3 对我们模型的增量（最小改动）

1. **记录域**（`work_reports`）加两列：`fields JSONB`（键值对，装上面那 8-10 个字段）与 `tags TEXT[]`
   （受控词表取值）——**渲染器与卡片协议一行不用改**（`fields`/`list`/`text` 原语已经支持）。
2. **词表**：新增一份"部门词表"数据（JSON：分类项 → 取值列表），随技能市场分发；服务端校验 `tags` 取值合法。
3. **周期**：`periodKey` 支持 `2026-10`（月）。视图默认按「项目 × 月」聚合，其次「人 × 月」。
4. **导出**：按他们的表形状生成 xlsx（五个 sheet 之一即可先做 01），让经理**继续用熟悉的产物**——
   我们的价值在"自动填"，不是"换个地方看"。
5. **回填**：支持把这五个表**导入**（幂等：按 项目编号+月份+工程师 去重），否则看到的是空台账，没人会用。

## 十、多部门差异：通用 JSON + 模板约束 + 服务端校验（2026-10-19 用户提出）

用户口径：_"是不是应用通用 json，但是通过 skill 约束内容和项目，方便不同部门不同的要求？"_ —— **对，但不能只有 skill。**

### 10.1 三层分工（少一层就会断在某处）

| 层             | 载体                                                         | 管什么                                                                      | 谁改它                                        |
| -------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------- | --------------------------------------------- |
| **作者向约束** | **skill**（+ 模板/示例）                                     | 告诉 agent 这个部门的字段、词表、必填项、语气、示例                         | **部门自己**，改完即生效，不发客户端版本      |
| **机器向契约** | **模板**（`schema.json` + `vocabulary.json`，随 skill 同包） | 字段名/类型/必填/长度上限/受控取值；**同一份东西同时喂给 agent 与服务端**   | **部门自己**（发新版 skill 即生效，见 §十三） |
| **事实边界**   | **服务端校验**                                               | 入库前按该模板校验；不合格 → 拒绝并把"缺什么/哪个取值不合法"回给 agent 去修 | 平台                                          |

**为什么不能只有 skill**：skill 是给模型的说明书，**软约束**。这一轮我们就亲眼见过 agent 漏字段、把内容写歪；
而台账要能被机器聚合、要能导出成 xlsx 给经理——格式一错，下游全废。所以：
**skill 负责"写得对"，模板+schema 负责"必须对"**，两者**同一份来源**（模板是 skill 包的一部分），
避免"文档说一套、校验做另一套"。

### 10.2 具体形状

- **模板包**（走 AIHub 技能市场分发）：`SKILL.md`（怎么问、怎么归纳）+ `vocabulary.json`（受控词表，
  如 `测试内容分类: ["5-编制配置项测试计划", "14-系统联试/联调", ...]`）+ `schema.json`（字段与必填）+
  `example.card.json`（一份填好的样例，agent 照它填）。
- **卡片类型带版本**：`card.type = "dept.qa.test-report"`、`card.version = 3`；渲染器**完全不认识它**，
  只按原语渲染（已实现）。**提交时带 `templateId + templateVersion`**，服务端按该版本校验——
  版本不能省，否则"改了模板"会把历史记录的含义一起改掉。
- **导出跟着模板走**：xlsx 的表头与列顺序由模板的字段定义生成，**不是写死的**。换部门/换模板，表头自动跟着变；
  他们的"01 测试情况表 / 03 问题表 / 04 售后表"各自就是一份模板实例。

### 10.3 一条重要反建议：骨架由平台定，部门只做扩展

如果放任"每个部门一套 JSON + 一套 skill"，很快就会变成**每个部门一张自己的表**，公司层面再也汇总不起来
（这正是他们现在五张表的由来，只不过那五张表恰好共享了同一套骨架）。

所以：

- **共享骨架（平台定义，不许改）**：归属（项目/部门/工程师/项目经理）+ 时间 + 对象 + **分类** + 内容 +
  **工作输出物** + 问题 + **审计四字段**（创建人/时间、最后编辑人/时间）。§九 勘察出来的五张表就是它的实例。
- **部门扩展位（模板定义）**：骨架内追加字段、追加词表取值、设必填与默认值。
- 这样"同一个人的同一段时间"在任何部门都能被同一条汇总逻辑读到，而部门的差异体现在**字段与词表**上。

### 10.4 落地清单（都在现有代码上增量）

1. 服务端：`work_reports` 已有 `fields`/`tags`；新增 `template_id`/`template_version` 两列 + 一个**通用
   schema 校验器**（模板 JSON → 校验 `fields`/`tags`）；校验失败返回结构化错误（哪个字段、什么原因），
   **让 agent 能自己修**（这条决定了闭环能不能自动跑起来）。
2. 客户端：渲染器与卡片协议**不动**；导出按模板列定义生成 xlsx。
3. 技能市场：新增"部门模板包"这一类别（skill + 词表 + schema + 样例），随 AIHub 分发与更新。
4. agent 流程：读模板 → 收集素材（会话/文件）→ 按模板填 → **本地先校验一次** → 提交 →
   服务端再校验（两道，前者省往返，后者是事实边界）。

## 十一、数据模型收敛：`work_records` 是骨架，`work_reports` 只是它的一个 type（2026-10-19 用户提出）

用户口径：_"work_reports 是不是也应该作为一个更通用的项目的子集？"_ —— **是，而且应该现在就改**（还没发给任何用户）。

### 11.1 为什么必须收敛

`work_reports`（title/summary/content/problems/period_key/recipient_ids…）是**为"汇报"这一个形状建的表**。
但 §九 的真实台账说明了三件事：

1. 他们的**五张表本来共享一套骨架**（归属/对象/时间/分类/内容/输出物/问题/审计），只是"每类一件事"分开记；
2. §十 又定了"共享骨架由平台定、部门只做扩展位"——骨架如果落在**每类一张表**上，这句就是空话；
3. 卡片那边我们刚吃过一次同样的教训：把"汇报"做成专用 `kind='report'`，每加一种就要发一次客户端。
   数据层如果照抄这个错，代价更大——**每加一类工作就要建表、改端点、改导出、改权限**。

### 11.2 目标形状

**一张 `work_records`**：

| 组           | 列                                                                                        | 为什么列化                                                       |
| ------------ | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 身份         | `id` / `org_id` / **`type`** / `template_id` / `template_version`                         | `type` + 模板决定校验器、默认视图与导出表头                      |
| 归属（骨架） | `author_id` / `department` / `project_id` / `project_name` / `engineer_id` / `manager_id` | **汇总就是按这几列 group by**（他们 725 行表按 项目×月×人 统计） |
| 时间         | `occurred_at` / `ended_at` / **`period_key`**（`2026-10`）                                | 月度视图、超期提醒都走这里                                       |
| 内容         | `title` / `summary` / `content` / `problems`                                              | 检索（pg_trgm）与预览要命中正文                                  |
| 扩展         | `fields JSONB` / `tags TEXT[]`                                                            | **只装模板声明的扩展位**（分类词表取值进 tags）                  |
| 产出         | `attachment_ids TEXT[]`                                                                   | 附件复用现有会话附件                                             |
| 投递         | `recipient_ids` / `message_id` / `status`                                                 | 汇报才用；其他类型留空                                           |
| 引用         | `ref_ids TEXT[]`（汇报引用了哪些记录 / 记录来自哪个会话）                                 | "汇报是聚合视图"要能追溯来源                                     |
| 审计         | `created_by`/`created_at`/`updated_by`/`updated_at` + `reviewed_by`/`reviewed_at`         | 对齐他们表里那**四个审计列**（§9.2）                             |

**规矩（防止退化成 JSON 垃圾场）**：

- **骨架字段必须列化**（可索引、可聚合、可导出）；**扩展只进 `fields JSONB`，且必须由模板声明**；
- `type` 与模板**一一对应**，服务端按 `(template_id, template_version)` 校验 `fields`/`tags`；
- 客户端渲染器与卡片协议**完全不感知 `type`**（只按原语渲染），导出表头由模板列定义生成。

**"汇报"在新模型里是什么**：`type = "report"` 的一条记录，`ref_ids` 指向它汇总的那些记录（或按 项目×月
现场聚合后物化）。于是 **记录 → 汇报 → 卡片消息** 是同一条链上的三个环节，而不是三张表、三套端点。

### 11.3 迁移（现在做几乎零成本）

还没发给任何用户，也没有真实数据（生产只有联调测试数据），所以：

1. 建 `work_records`，把 `work_reports` 现有数据搬过去（`type='report'`，`template_id='platform.report.v1'`）；
2. **API 保持兼容**：`POST/GET /api/reports` 保留为兼容层（内部读写 `work_records`），客户端与技能不用改；
3. 新增通用端点 `POST/GET /api/records`（带 `type`/`template`/`period`/`project` 过滤）；
4. 旧表先留着不删（回滚材料），但**不再写**。

**不要走的那条路**：在 `work_reports` 上原地加列。那样半年后就会有 `test_records`、`issue_records`、
`after_sales_records`……正好复刻他们现在这五张表，而且公司层永远汇总不起来。

### 11.4 与 taskjournal 的边界（别混）

- **msgbus 的 `work_records`** = **人对外的业务台账**：给领导看、要导出成他们的 xlsx、有权限与回执、
  一行就是一件"要报出去的事"；
- **taskjournal** = **agent 的工作流水**（任务/活动/产物/证据，给 agent 自己、给被动提取用）；
- 两者的连接点是**引用**（记录可带 `source: {conversationId, taskId}`），**不合并成一张表**——
  一个是"业务事实"，一个是"过程事件"，混在一起会让两边都变脏。

## 十二、通用抽象：别自创，对齐既有标准（2026-10-19 用户追问）

用户口径：_"`/api/records` 也太窄了，有没有大家都在用的更通用的抽象？"_ —— **有，而且我那个名字本身就是症状**：
"records" 是我给这一个功能起的名字，说明我心里还是"一个功能一套接口"。业界处理"**一个信封 + 很多类型 +
不同组织不同要求**"这件事，已经有几套很成熟的抽象：

| 抽象                                                                | 它管什么                                                                                                                                                                 | 适不适合我们                                                                                                                   |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| **JSON:API**（jsonapi.org）                                         | 资源对象＝`{ type, id, attributes, relationships, links }`；统一 `filter[…]` / `sort` / `page[…]` / `include` / `fields[…]`；错误用 `errors[]` 数组；**type 是一等公民** | ✅ **最合适**：术语与 JS/zod 生态贴合，`relationships` 正好表达"汇报引用了哪些记录 / 记录来自哪个会话"，`include` 正好做旁加载 |
| **Kubernetes 风格**（`apiVersion/kind/metadata/spec/status` + CRD） | 声明式资源 + **类型作为数据注册**（新类型＝一份 CRD＋校验 schema）＋ 版本化（`v1alpha1→v1`）                                                                             | ✅ **借"类型注册"这一层**：我们 §十 的"模板"就是 CRD 的角色；但不必引入它的控制器语义与 `spec/status` 命名                     |
| **FHIR**（医疗，`resourceType` + `extension` + **Profile**）        | 同一信封 + 各机构用 **Profile** 约束字段（必填/词表/基数），`Bundle` 做集合                                                                                              | ✅ 概念上最贴近"不同部门不同要求"——**Profile 就是我们说的模板**；但整套规范太重，只借概念                                      |
| **Google AIP**（AIP-131/132/158/160）                               | 标准方法（List/Get/Create/Patch）+ **`filter` 表达式** + `page_size/page_token` 游标                                                                                     | ✅ 借它的**列表语义**：一个 List 配 filter/排序/游标，而不是每类手写端点                                                       |
| **CloudEvents 1.0**（CNCF）                                         | 事件信封：`{ specversion, type, source, subject, data }`                                                                                                                 | ✅ 用在**投递/通知**那一侧（提交记录 → 广播一个事件），我们的 `message` 帧已经是这个形状的雏形                                 |
| OData / GraphQL                                                     | 通用查询语言（`$filter/$expand`；或 schema 驱动的单端点）                                                                                                                | ❌ 太重：OData 表达式语言完整实现成本高；GraphQL 会给我们增加一整套服务端 schema 与鉴权层，收益不匹配                          |

### 12.1 我的建议（借形状，不领合规）

**采纳 JSON:API 的资源形状 + AIP 的列表语义 + k8s/FHIR 的"类型即数据"**，但**不宣称合规**——
我们只借那些真正决定可扩展性的部分：

1. **统一信封**（JSON:API 形态，客户端已有 zod，天然对口）：
   `{ data: { type, id, attributes: {...}, relationships: { project: { data: {type,id} } } } , included?: [...] }`，
   错误用 `{ errors: [{ status, code, detail, source }] }`——**`source` 能指到具体字段**，这正是 §10.1
   "让 agent 自己修"需要的结构化错误。
2. **一个集合端点 + 标准查询语法**（不是每类一个端点）：
   `GET /api/work-items?filter[type]=dept.qa.test-record&filter[period]=2026-10&filter[project]=1609&sort=-occurredAt&page[size]=50&include=refs`
   —— 路径名从"records"改为**领域中性**的 `work-items`（业界对"一件要被追踪的工作"最常见的叫法；
   Jira 叫 issue、Salesforce 叫 SObject、SAP 叫 business object，`work-item` 是其中最不被某一家绑定的）。
   **新增类型不写新端点**：`type` 是查询参数，不是路径段。
3. **类型即数据**（k8s CRD / FHIR Profile 的角色）：§十 的模板就是它——`(type, template_version)` →
   校验器 + 默认视图 + 导出表头；服务端只维护**一个通用校验/序列化管道**。
4. **事件侧**：提交后广播的事件按 CloudEvents 形状组织（`type: "org.ucas.work-item.submitted"`,
   `source: "/services/msgbus"`, `subject: "<id>"`, `data: <card 文档>`）——这样卡片消息、通知、
   将来的 webhook/订阅都共用同一个信封。

### 12.2 与现状的关系（要改的其实很少）

- 现有 IM 那套手写 REST（`{conversations: [...]}` / `{error, message}`）**不动**——它是"少数几个固定资源"，
  改成 JSON:API 只有审美收益；**要统一的是新起的"多类型台账"这一面**（work-items）。
- **`/api/reports` 作为兼容层保留**（内部读写 `work_records`/work-items），客户端与技能不用改。
- 命名收口：表 `work_records` → 对外资源名 `work-item`（`type` 为子类型，如 `report` / `test-record` /
  `issue` / `after-sales`）。表名可以继续叫 records，**对外只有一个资源名**。

#### 12.3 已落地（2026-10-19）

- **表**：`work_records`（骨架列化：org/type/模板版本/归属/时间/周期/标题正文/问题/`fields`/`tags`/附件/
  收件人/`ref_ids`/状态/**审计四字段+回执**）；索引按 `(org,type,occurred_at,id)`、`(author,occurred_at)`、
  `(org,project,period_key)`——**汇总就是按这几列 group by**。
- **端点**：`POST/GET /api/work-items` + `GET /api/work-items/:id` + `POST /api/work-items/:id/review`。
  信封是 JSON:API 形状（`{data:{type,id,attributes,relationships,links}}`）；查询支持
  `filter[type|period|project|author|status]` + `sort`（`-occurredAt` 默认倒序）+ `page[size]` +
  **`page[cursor]`（keyset 游标，不用偏移）**；错误走 `{errors:[{status,code,detail}]}`。
- **兼容层**：`/api/reports` 一行没改对外形状，内部读写 `work_records`（`type='report'`）；
  历史 `work_reports` 数据已迁入（3 条）；旧表保留作回滚材料，不再写入。
- **nginx**：`/api/work-items` 两个 server 块都加了（并 `restart nginx` 换 inode）。

**生产实测**：

- `GET /api/work-items?filter[type]=report&page[size]=2` → 3 条、信封含 `relationships`（author/project/manager）与 `links.self`；
- **新类型零新端点**：`POST` 一条 `type=dept.qa.test-record`（带 `fields: {测试方式:"AI测试", 工作输出物:…}`）→ 201，扩展字段原样落库；

- **客户端无感**：汇报页仍列 3 条、详情弹窗正常、会话里 3 张卡片照旧（兼容层保住了老形状）。

## 十三、部门自服务：模板随**部门自己的 skill** 发布，运维不在链上（2026-10-19 用户纠正）

用户口径：_"不同部门不同要求，应该还是通过部门自己的 skill 实现，而不是运维去不停修改。"_ —— **成立，
而且我上一版 §10.1 写的"部门 + 平台评审"是多余的流程，撤回**。评审是部门内部的事；平台只该维护
**一套通用能力**，然后**再也不碰**。

### 13.1 职责边界（改完这条，运维就退出了）

| 角色             | 负责什么                                                                  | 变更频率                 |
| ---------------- | ------------------------------------------------------------------------- | ------------------------ |
| **平台（我们）** | 骨架（§11.2 那些列）+ **一个通用校验/序列化/渲染/导出管道**               | 装完基本不动             |
| **部门**         | 自己的 skill 包：提示词 + **字段定义** + **词表** + 样例 + **导出列映射** | 想改就改，**发布即生效** |

**发布通道用现成的**：AIHub 技能市场本来就是**公司受控的技能来源**（内部市场、独立成段、版本可迭代）。
部门把模板**放进自己的 skill 包**一起发：

```
dept-qa-report/            ← 部门自己的 skill 包（技能市场里的一件）
  SKILL.md                 ← 怎么问、怎么归纳、什么时候必须追问
  schema.json              ← 字段定义：名字/类型/必填/长度/白名单校验器
  vocabulary.json          ← 受控词表（"14-系统联试/联调"、"AI测试"…）
  export.columns.json      ← 导出 xlsx 的列顺序与表头（部门自己管）
  example.card.json        ← 一份填好的样例（agent 照它填）
```

部门改字段 → **在技能市场发新版本** → 服务端按 TTL 拉取并缓存 `(templateId, templateVersion)` → 立即生效。
**全程没有运维干预、没有发版、没有改配置**（首次接线除外）。

### 13.2 校验怎么做到"部门自服务"又不失控

三条设计（这是这一节的要害）：

1. **模板是数据，不是代码**：`schema.json` 里只能用**白名单校验器**（`required` / `oneOf`（词表）/
   `range` / `length` / `pattern`（受限正则）/ `dateFormat`）。**绝不开放"部门自带校验脚本"**——
   那等于让部门往服务端注入代码。校验管道只有一份实现，永不因部门而改。
2. **版本冻结**：记录里存 `template_id` + `template_version`（+ schema 哈希）。模板改版只能出新版本；
   **旧记录永远按它当时的定义解释**，所以历史导出与详情不会因为部门改字段而变形。
3. **拉不到模板时不拒绝提交**（重要）：技能市场抖动/新部门还没发模板时，降级为**只校验骨架**并给记录打上
   `validation: "skeleton-only"` 标记（**可见状态，不是静默通过**）；等模板可用后可重新校验。
   理由是硬的：**"交不了周报"比"字段宽松"严重得多**——前者会让人直接放弃这个工具。

### 13.3 仍然不开放的（骨架与安全边界）

- **骨架不许部门改**（归属/时间/周期/标题正文/问题/审计四字段）：否则公司层汇总不起来（§10.3）。
  部门只能在骨架里**追加** `fields`/词表取值/必填/导出列。
- **卡片渲染器不认识任何模板**（只按原语渲染，已实现）——所以"部门自服务"不需要客户端发版。
- 服务端拉取技能市场需要一个内部通道（市场 API 或共享目录），这是**一次性接线**；之后部门自助。

## 十四、审核人路由：部门自己能改，规则在服务端解析（2026-10-19 用户提出）

用户口径：_"部门内部应该能够修改审批人，skill 按规则自动推送到审核吧"_。

### 14.1 先把边界说准（我之前那句"不做审批流"要收窄）

我此前写的"不做审批流"指的是**不做通用审批引擎**——多级会签、条件分支、或签/并签、超时升级、审批表单校验，
那是钉钉/企微审批那个量级的产品，我们不自建（§六.1）。但**"这份东西该谁看、谁确认了"必须有**，
而且我们已经有了它的骨架：`status: submitted | reviewed | returned`、`reviewed_by/reviewed_at`。

**所以准确定位是：只做"路由 + 送达 + 已阅/退回 + 留痕"，不做"审批流程"。** 四件不做：
多级、分支、超时升级、会签。这条边界要写死在实现里，否则半年后就会长成一个审批引擎。

### 14.2 两张表分开：形状随 skill 走，人随部门数据走

| 内容                         | 放哪                             | 为什么                                                   |
| ---------------------------- | -------------------------------- | -------------------------------------------------------- |
| 字段/词表/导出列（**形状**） | **部门自己的 skill 包**（§十三） | 低频、需要版本冻结                                       |
| **谁审**（路由规则）         | **服务端的部门路由数据**         | 高频、跟着组织与项目变动；**改一个人名不该发一版 skill** |

路由规则的最小形态（刻意不做匹配语言）：

```
{ department, templateId?, projectId?, authorId?, reviewerIds[], fallback?: reviewerIds[] }
```

匹配维度就上面这几个（类型/项目/作者/部门），**优先级 + 兜底**：按"最具体优先"（项目 > 部门 > 兜底），
命中即用；都不命中则回落到部门默认审核人。**不做条件表达式、不做多级、不做会签**。

### 14.3 "skill 按规则自动推送"的准确含义：**规则由服务端解析，agent 不判人**

- 提交记录时**可以不带收件人**，服务端按路由规则解析出 reviewer 并投递卡片（现有投递链路不变）；
- **agent/skill 不自己判断谁该审**——那是"把组织规则复制到提示词里"，改一次规则就要动所有 skill，
  而且模型会猜错。只在**规则缺失/不命中且没有兜底**时，skill 才问用户"这份送给谁"，
  并把用户的选择作为**规则建议**回传（部门管理员确认后写进路由表）——这就是"越用越顺"的路径。
- 返回里带 `resolvedReviewers`，agent 据此回一句"已送 X 审核"（用户看得到它送给了谁，可纠错）。

### 14.4 审核动作与退回（在已有状态机上补两处）

1. **已阅/退回**：`POST /api/work-items/:id/review { status, comment? }`——新增 `comment`（退回必须带原因，
   否则作者不知道改什么）；审计里留"谁、何时、什么意见"。
2. **退回后能改再交**：退回 → 作者更新**同一条记录**（`updated_by/updated_at` 留痕）→ 状态回 `submitted`。
   **不生成新记录**：它还是"同一份要报出去的东西"，分成两条会让"这条报过了没"变得无法回答。
3. **通知**：审核人收到卡片 + 系统通知（现成）；作者收到"已阅/退回（含意见）"的提示——
   后半句需要一个反向通知，先复用会话里的卡片/系统消息，不新增通道。

### 14.5 谁能改路由规则（这条会补掉一个早先的缺口）

- 我们库里**没有"谁是部门负责人"这个数据**（很早以前就发现了）。路由规则本质上就是**部门 → 审核人**，
  所以这张表**顺便把那个缺口补上**：`department_routing`（部门、审核人、维护人、更新时间）。
- P0：由 **org_admin 初始维护**（公司层面三五个人）；界面上按部门分组编辑。
- P1：开放给**部门负责人**（本部门规则可改，跨部门不可见）——这需要"部门负责人"这个字段，
  可以由 org_admin 指定（而不是去企微同步组织架构，那会引入新的同步面）。
- 规则变更**必须留审计**（谁在何时把审核人从 A 改成 B）：它决定了"东西送给谁"，是治理数据。

### 14.4 之一、「已阅」是**回执**，不靠领导动手（2026-10-19 用户口径）

用户原话：_"可以增加一个'已阅'状态，作为一个回执状态，领导就算不点击也没关系。"_

**改法**：把「已阅」从**按钮**变成**回执**——审核人**读到那张卡片**（IM 已读游标越过它）时，系统自动
落一次回执：记录上写 `seen_by/seen_at`，`submitted` 的记录顺手推到 `reviewed`（`reviewed_by/at` 与回执
同人同时刻），并把那张卡片收尾成「已阅」（摘掉动作、补徽标与结论段）。**手上要动的只剩「退回」**
（唯一需要表达"这不行"的分支，且必须写意见）。

- **触发搭在已读事件上**（`store/workItemReceipt.ts` ← `POST /conversations/:id/read` 的旁路钩子）：
  不新增客户端上报、不新增通道。旁路**失败不影响已读本身**（已读是聊天主干，回执只是搭上去的）。
- **三条边界**：① 只有**收件人**能触发（`recipient_ids` 里且不是作者）——作者自己翻看自己的卡片不算；
  ② **只前进不覆盖**：已 `reviewed/returned` 的记录不动（退回后重看不会把结论改掉）；
  ③ **老卡片也吃这条规则**（判定用记录上的 `recipient_ids`，不依赖卡片里的 `to`，那是后加的）。
- **卡片动作因此变了**：`buildWorkItemCard` 不再投「已阅」按钮，卡片只剩「查看详情」+「退回」。
  客户端那条 `review` 分派**保留**——库里已投出的老卡片还带着它，点了仍然有效。
- **口径影响**：台账里的 `reviewed` 现在可能是"系统在领导读到时代为落下的"。对部门的意思是
  **"这份东西领导看过了"有据可查**，而不再取决于他记不记得点一下；导出列里本来就没有审核状态列，xlsx 不受影响。

**真机验证（2026-10-19，生产 msgbus）**：

| 场景                                                             | 结果                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 作者＝我、审核人＝测试账号（**没有客户端**）→ 投递后等 15 秒     | 记录**仍是 `submitted`**、`seen_by` 为空（没有任何东西自己触发）                                        |
| 再做一次审核人客户端的动作：`POST /read`（等价于"他打开了会话"） | 记录自动变 `reviewed`，`seen_by`＝测试账号、`seen_at` 落上；那张卡片变成「已阅」徽标 + 只剩「查看详情」 |
| 我用应用打开那个 DM（**一下都没点**）                            | 新投的卡片一到就自动变「已阅」——因为客户端在会话打开时推已读，这正是"不点也算已阅"                      |
| 作者视角                                                         | 回执落地后，"你提交的 · 等审核人处理"那行自动消失，换成「已阅」徽标 + 审核结果段                        |

**一个诚实的边界**：触发条件是"客户端推了已读游标"，而客户端的已读语义是**会话打开（含它在后台被选中）
就算读到**——不是像素级"滚到那张卡片"。这与 IM 的已读语义一致，但比"眼睛真的看过"宽松；要更严就得让客户端
上报"卡片进入视口"，那是另一笔改动。

### 14.4 之二、负责人通过 agent 拿汇总：入口、权限与三个必须修的坑（2026-10-19 验证）

用户要求：_"需要验证一下负责人能够通过 agent 获取汇报汇总。"_ 结果**这条路原本是断的**——
不是权限没设计，而是缺入口 + 三个真缺陷，全都靠"真去跑一遍"才暴露：

| #   | 问题                                      | 现象                                                                                                               | 修法                                                                                                                                                         |
| --- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **角色是层级制，msgbus 却写等值判断**     | 控制面按库里角色发 token（`super_admin`），而部门闸门只认 `'org_admin'` → **平台所有者被自己的系统 403**           | 收口到 `auth/roles.ts` 的 `isOrgAdmin()`（`org_admin` / `super_admin` 都算），两处闸门改用                                                                   |
| 2   | **agent 没有"拉部门"的入口**              | `export-ledger.mjs` 不支持 `--department`，也没有"我能汇总什么"的问法                                              | 加 `GET /api/work-items/scope`（谁、能汇总哪些部门）+ `rollup-scope.mjs`（人话输出）+ `export-ledger --department`；SKILL 固化"先问权限再拉，拉不到要如实说" |
| 3   | **技能包里裸 import 一个包 → 安装后必崩** | `import "exceljs"` 只在 monorepo 里解析得到；agent 在用户技能根跑（**没有 node_modules**）→ `ERR_MODULE_NOT_FOUND` | 换成零依赖写出器 `scripts/xlsx-lite.mjs`（zip + XML，不压缩存条目）；回归测试把技能包**拷到临时目录再跑**，并静态禁止裸包导入                                |
| 4   | **导出读不到模板字段**                    | `cellValue` 只读平铺属性，而模板字段在 `attributes.fields` 里 → 台账里"测试方式/测试数量/产品总数"**一直是空列**   | `attributes[field] ?? attributes.fields?.[field]`                                                                                                            |
| 5   | **人员列写 UUID**                         | 「测试工程师/创建人/最后编辑人」导出成 `11111111-2222-…`，部门没法用                                               | 导出时拉一次通讯录解析人名；解析不到就**保留 id**（不编名字）                                                                                                |
| 6   | **记录不填部门就从汇总里消失**            | 台账只按 `department` 过滤，而调用方（agent）不填 → 负责人拉本部门**看不到自己人的记录**                           | 服务端缺省用作者的部门（来自白名单快照），填了以调用方为准                                                                                                   |

**口径**：`rollup-scope.mjs` 是 agent 的**第一步**——它输出人话，例如
「你：研发管理部（平台管理员）／能按部门汇总：测试与服务保障部」。`canRollup` 为空就如实说
"只有负责人能汇总整个部门"，**绝不允许把"拉不到"说成"这个月没有记录"**（那是假消息）。

**真机验证（2026-10-19，生产）**：

| 环节                                                                     | 结果                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 用**你自己**的登录身份（`super_admin`）跑 `rollup-scope.mjs`             | 「你：研发管理部（平台管理员）／能按部门汇总：测试与服务保障部」，并提示"你自己的部门不在可汇总范围里"                                                                                                                                     |
| `export-ledger.mjs --department 测试与服务保障部 --period 2026-10`       | 1 行；模板字段齐全（测试方式=AI测试、测试数量=4、产品总数=2…）、人员列是人名（IM 测试账号 / 辛晓华）、所属部门正确                                                                                                                         |
| **在应用里对 agent 说**「汇总测试与服务保障部 2026-10 的记录并导出台账」 | agent 自己先跑 scope、再导出、然后给出汇总：**共 1 条、IM 测试账号报的、项目 PD读出电子学、已审核无积压**；并**主动点出两个诚实细节**（该记录只过骨架校验所以模板必填列空；另有两条第 2026-08 的记录还卡在待审）——没有把"看不到"说成"没有" |
| 非负责人按部门拉                                                         | 403，错误文案说清是权限问题（"这是权限，不是没有数据"）                                                                                                                                                                                    |

### 14.4 之三、端到端实测：汇报 → 投递 → 回执 → 汇总（2026-10-19 按用户要求跑通一遍）

用户要求："e2e 测试汇报及汇总"。下面是**一条链走到底**的实测记录（生产 msgbus + dev 客户端 + 已安装技能包），
每步都同时核了界面与服务端状态：

| 步           | 动作                                                              | 实测结果                                                                                                                                                      |
| ------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 起草       | 对 agent 说"把今天这几件事写成测试部工作记录"（素材取自本周会话） | 草稿进暂存箱 `#20261020-085533-draft`（`staged`）；卡片渲染出来，底部写着「草稿在本机：#… · 路径」，两个按钮「汇报 / 暂存」                                   |
| 2 汇报       | **点卡片上的「汇报」**（沙箱按钮 → follow-up）                    | 宿主确认弹窗预填 `汇报：工作项卡片动作闭环、已阅回执与部门汇总导出验证` → 发送 → agent 跑技能提交                                                             |
| 3 落库       | ——                                                                | 记录落进测试与服务保障部 / 2026-10，`validation: template`（按模板校验通过）；暂存箱那条自动变 `submitted`（`--draft-id` 生效）                               |
| 4 投递       | ——                                                                | 卡片进作者↔审核人的 DM（审核人＝IM 测试账号）                                                                                                                 |
| 5 作者视角   | 在应用里看那张卡                                                  | 只剩「查看详情」+ 一行「你提交的 · 等审核人处理」——**没有点不动的审核按钮**                                                                                   |
| 6 接收方读到 | 模拟他的客户端推已读（`POST /read`）                              | 记录自动 `reviewed`，`seen_by`＝审核人；作者侧那张卡**实时**变成「已阅」徽标 + 「审核结果」段，等待行消失                                                     |
| 7 汇总       | 对 agent 说"再汇总一次本部门 2026-10 并导出"                      | agent 自己跑 scope → 导出 → 汇报：**共 3 条**、逐条点名（谁提交、什么内容），并明确说"**还有 1 条没有被审核人看过**（无已读回执、状态 submitted）"；xlsx 3 行 |

**这一轮暴露的两件事**（都已处理）：

1. **审核人＝作者自己时，卡片不会投递**（投递层按设计跳过"给自己发卡"），而当时是**静默**的——
   提交成功、看起来一切正常，但对方永远收不到卡。已补：`meta.hint = reviewer is the author: no card delivered`，
   agent 与脚本据此能说清"要换个人审"。测试：`workItemsReview.test.ts` 的「投递的边界情形」。
2. **本地模板校验器真的拦住了不合格的提交**（第一次提交被拒：`fields.项目状态` / `fields.工作输出物` 必填），
   补上后才过——这条是"部门自服务"能站住的证据：校验在**提交前**发生，不是等领导发现字段空着。

顺带记一条 agent 的**诚实行为**（值得保留）：它主动指出"第 3 条的审核回执是 IM 测试账号落的，
如果它本该由你审，审核人设错了"——它读的是回执数据，而不是猜。

### 14.4 之四、催办：固定时间审查，没收到的自动提醒（2026-10-19 用户要求）

用户原话：_"测试定时任务，服务于负责人，固定时间审查汇报，如果没有收到的自动发送提示消息。"_

**做法**（跑在 msgbus：数据与投递都在它那边；控制面的"每分钟 tick、各自按日/周触发"是现成的模式）：

- **谁该交**＝白名单快照里该部门的成员（`departmentsOf` 的反向），**不含负责人自己**（不催领导）。
- **算不算交**＝该部门 + 该周期（默认当月，与台账口径一致）里有记录（`author_email` 去重）。周期可传，便于补跑历史周期。
- **没交的**：在他与**负责人的 DM** 里放一张提醒卡（作者＝负责人，卡片带「系统自动提醒」徽标 + 回执式措辞），
  这样成员看到的是"部门在催"，而负责人自己的会话列表里能看到催了谁。
- **负责人的总览**：不另开通道——**问 agent 就有**（`rollup-scope` + 按部门拉，已经能回答"谁还没交"，
  见 §14.4 之二）；任务的触发接口**返回本次计划**（已交/未交名单），运维与 agent 都能读。
- **幂等**：`work_reminders(user_id, period_key, kind)` 唯一 → 同一周期同一人只催一次（`force` 才重发）。
  没这条就会变成"每天骚扰一遍"，那比不催更糟。
- **默认关闭**：`WORK_REPORT_REMINDER_ENABLED=1` 才启动定时器（默认不动）；固定时刻用
  `WORK_REPORT_REMINDER_HOUR`（本地时，默认 17）与可选 `WORK_REPORT_REMINDER_DOW`（0=周日，缺省每天）。
- **手动触发**：`POST /api/im/internal/report-reminders/run`（服务令牌 `x-internal-token`，与白名单快照同一个），
  支持 `{ dryRun: true }`（只算计划不发）、`{ onlyUserIds: [...] }`（只催指定的人——**真机验证时用它避免打扰真实同事**）、
  `{ force: true }`。

**真机验证（2026-10-19）**：dry-run 出计划（谁该交、谁已交、谁未交）→ 用 `onlyUserIds` 只催测试账号一条 →
在应用里确认那张提醒卡（措辞、徽标、来自负责人）→ 再跑一次确认**幂等**（提示已催过，不发第二条）。

**真机验证（2026-10-19，生产 msgbus）**：

| 场景                                                      | 结果                                                                                                                                                                          |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dryRun` 看计划（2026-10）                                | 应报 14 人 / 已交 2 人（辛晓华、IM 测试账号——正好是造过记录的两个人）/ 未交 13 人；**发出 0 条**（dry-run 一条都不发）                                                        |
| 只催测试账号（`onlyUserIds`，用一个它没交的周期 2026-09） | **发出 1 条**；卡片作者＝负责人吴鹏、类型 `platform.work-item/reminder`、徽标「系统自动提醒」、标题「2026-09 的工作记录还没交」、`to`＝收件人；**无动作按钮**（没什么可点的） |
| 同一周期立刻再跑                                          | 发出 0、跳过 1（**幂等**：不会变成每天骚扰）                                                                                                                                  |
| 已经交过的人                                              | 不会被催（测试账号在 2026-10 已交 → 不在未交名单里）                                                                                                                          |
| 定时器                                                    | 生产 `.env` **未配置开关**＝关闭（默认不自动发消息）；打开只需 `WORK_REPORT_REMINDER_ENABLED=1`（可配 `WORK_REPORT_REMINDER_HOUR`／`_DOW`）                                   |

**实现时踩到并修掉的两个坑**（都有回归测试）：

1. **`one()` 查不到行返回 `undefined` 而不是 `null`**：幂等判据写成 `!== null` 恒为真 → **所有人都被当成"已催过"，一条都发不出去**。
   是"dry-run 之外一个都不发"的用例抓到的——这类静默失败正是要靠"反向断言"（本该发却没发）才看得见。
2. **快照顶层的 `orgIds` 是标签（`beijing`），不是记录里存的组织 UUID**：拿它过滤 `work_records.org_id` 一条都查不到，
   计划显示"已交 0 人"（明明有 2 条记录）。改成**按人取组织 id**（快照里 users 带真实 orgId），并把这个不一致钉进测试。

**边界修正（2026-10-19 用户口径：`"定时任务直接在 uwork 做就行吧，msgbus 只是通信渠道"`）**

第一版把"固定时间 + 催谁 + 说什么"整套做进了 msgbus（定时器 + 专用端点 + `work_reminders` 表）。这条边界是错的：
**周期与策略是业务，属于 UWork**；msgbus 只该负责"把消息送到"。改后的分工：

| 层                               | 负责                                         | 落点                                                                                                     |
| -------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------- |

**一条必须知道的语义**：提醒的**作者＝运行者**（DM 是"我 ↔ 成员"）。所以真正的"催到人"应当由

（语义不对，也可能让人误会）。这也是为什么先在 `--dry-run` 形态交付：名单先给负责人看。

但**要建在 app 自己的实例里**才看得到（app 的数据根是 `~/.uwork`，CLI 会话是 `~/.zcode`——两边的
`tasks-index.sqlite` 不是同一个；本会话建的那条已删）。在应用里创建只需走「自动化 → 创建定时任务」，
或对 app 的 agent 说一句"每周五 17:00 跑 remind-missing"。

**E2E 实测（2026-10-19，全程由我做，未打扰任何同事）**：用户要求"你自己进行 e2e 测试"。做法与证据：

**顺手发现一条宿主护栏（值得记住）**：**不允许在"定时任务的运行会话"里再创建定时任务**——
`Cannot create a scheduled task inside a session that already belongs to a scheduled task`。
而且**这个标记不随任务跑完解除**：那条被投递过的会话永久不能再用来建任务（我连试三次都被拒）。
所以：**周期任务要在普通会话里建一次**（或先「新建任务」再用新会话建）。这条护栏本身是好的（防任务自我繁殖），
但它把"在同一个会话里连建两条"变成了不可能——排期配置要换个会话做。

**仍未完成的一步（诚实记录）**：**每周五 17:00 那条周期任务还没建上**。原因是我想在 app 里再建一条时，
CDP 合成事件点不动「新建任务」（⌘N 与按钮都试过，视图不切），于是三次尝试都落在同一个被占用的会话里被拒。
人工路径只需一步：**在 app 里点「新建任务」→ 对 agent 说「每周五 17:00 跑 remind-missing --dry-run，把名单报给我」**。
（要"真催到人"时，这一步应当在**部门负责人本人的账号**里做——提醒的作者就是运行者。）

## 十五、"部门负责人"从哪来（2026-10-19 用户追问）

用户问：_"部门负责人如何确定"_。查完我们自己的代码，答案是：**这个数据我们已经在拉，只是没存下来**——
不需要新接口、不需要新授权、不需要人工维护。

### 15.1 三个来源（按"具体 → 兜底"排序）

| 优先级 | 来源                                                       | 数据在哪                                                                                       | 特点                                                                               |
| ------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1      | **记录自带的收件人**（提交时指定，或记录里的 `managerId`） | `work_records.recipient_ids` / `manager_id`（骨架里已经留了这两列）                            | 最准：**这条具体送给谁**由提交的人/记录决定                                        |
| 2      | **项目级审核人**                                           | 待建：`project_reviewers`（project → reviewer）                                                | 他们的表里每行都有"项目经理"——测试部是服务方，**审核人常常就是项目经理**（跨部门） |
| 3      | **部门路由规则**（部门 + 模板 → 审核人）                   | 待建：`department_routing`（§14.5）                                                            | 部门自助维护，覆盖"本部门自己的事"                                                 |
| 4      | **企微部门负责人（自动同步）**                             | **`/cgi-bin/department/list` 的 `department_leader`** 与 **`/cgi-bin/user/get` 的 `isleader`** | **兜底**：保证"永远有个人能收到"，不会出现"没人可送"                               |
| 5      | 都没有 → skill 问用户                                      | —                                                                                              | 用户的选择作为**规则建议**回传（§14.3）                                            |

### 15.2 事实核对（我们今天的代码里）

- 我们**已经在调** `POST/GET /cgi-bin/department/list`（`control-plane/src/auth/wecom.ts` 的 `getDepartmentMap`），
  但只读了 `id`/`name` 建映射——**响应里每个部门还带 `department_leader: string[]`（部门负责人的 userid 列表）**，
  我们把它丢掉了；
- 我们**也已经在调** `/cgi-bin/user/get`（`getUserByCode` 的 Step 3），接口里声明了 `department/position/mobile/email`，
  但**没声明也没读 `isleader`（是否部门负责人）与 `main_department`（主部门）**；
- 我们的 `users` 表存了 name/email/avatar/department(字符串)/position/mobile——**没有"是否部门负责人"这一列**。

也就是说：**加两行解析 + 一列落库**，部门负责人就是自动同步的（跟着企微组织架构走，不需要人维护）。
`main_department` 还顺手解决"一个人挂多个部门时以哪个为主"（比现在按逗号串切分第一段更权威）。

**实现时要核对一次字段名**（企微文档里的 `department_leader` / `isleader` / `main_department`）——
最省事的核对方式：在 `getDepartmentMap` 里临时打一行原始响应日志（这两个接口我们本来就在调，不新增权限）。

### 15.3 与"审批人可改"的关系（用户上一条要求的落点）

- **自动同步不等于不可改**：企微给的是**默认值/兜底**；部门要改谁审 → 改的是**路由表**（第 3 层），
  不改企微组织架构（那会影响全公司的组织数据，权限也不该在我们这）。
- 三层一起工作时，**优先级必须写清并让用户可见**（"已送 X 审核"），否则"我明明改过审核人，怎么还送给了他"
  会成为最常见的报障——**规则命中哪一条要有解释**（返回里带 `resolvedBy: "record" | "project" | "department" | "wecom" | "ask"`）。

### 15.4 一个已知限制（先说清）

路由表可以配**多个**审核人，但**投递与附件作用域目前是单收件人**（附件挂在"作者与某个收件人的单聊"里，
见 §三③ 的 P0 限制）。所以多审核人要先把附件作用域改成**记录级**（附件归记录，不归会话）。
**在那之前：一名主审核人 + 若干"抄送"** 是能落地的折中（抄送的人收到卡片但附件下载会 403——所以更干净的做法是
先只支持单审核人，把"抄送"与"多审核人"一起放到附件作用域那一刀）。

## 十六、限制必须随模板交付，而且可执行（2026-10-19 用户要求）

用户口径：_"限制需要在 skill 模板中提供，防止部门自定义时不清楚。"_ —— 对。我们前面把边界写在**自己的 spec**
里（§10.3/§13.3/§14.1），但**部门改模板的人看不到这份 spec**；只靠口头约定，第一次自定义就会越界，然后
在运行期才炸（甚至不炸，只是数据变形）。

### 16.1 限制的载体：平台定义**一处**，随模板分发**两份形态**

| 形态                       | 给谁看                                                 | 内容                                                                     |
| -------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| **`PLATFORM-CONTRACT.md`** | **人**（部门管理员、写 skill 的人、agent）             | "你可以改什么 / 不可以改什么"的人话清单 + 例子                           |
| **`contract.json`**        | **机器**（部门本地校验、服务端校验、agent 填卡前校验） | 骨架字段名单、允许的校验器白名单、字段/长度/数量上限、周期格式、版本规则 |

**由平台生成、单一来源**（`platform.contract.v1`）：平台改限制只有这一处要更新，随技能市场分发到每个部门包；
**禁止在部门模板里各写一份**——那就是"文档说一套、校验做另一套"的老毛病。部门 `SKILL.md` 只**引用**它
（"你的字段必须满足 PLATFORM-CONTRACT 的第 3 节"），不复制。

### 16.2 限制清单（要写进 contract 的具体条目）

**只读（部门不能动）**：骨架字段名单（归属 / 时间 / 周期 / 标题正文 / 问题 / 审计四字段）——可以引用，
不能重命名、删除、改类型；周期格式（`YYYY-MM` / `YYYY-Www`）；消息与卡片协议；渲染原语集合。

**可改（部门自服务）**：追加 `fields` 字段与词表取值；在允许范围内设必填/默认值；调整**导出列顺序与表头**；
写 SKILL.md 的提问、归纳规则与样例。

**硬上限（防止把台账用坏）**：`fields` ≤ 40 项、单项文本 ≤ 2000 字符、`tags` ≤ 20 项、单个词表 ≤ 200 个取值、
模板包 ≤ 1 MB；**不允许**自带校验脚本/任意代码（只有 `required`/`oneOf`/`range`/`length`/受限 `pattern`/`dateFormat`）。

**版本与词表两条纪律**：改了就发**新版本号**，不要改已发布的版本（旧记录按旧版解释，§13.2）；
词表里**用过的取值不要删除**，要弃用就标 `deprecated`——否则历史记录会出现"取值不在词表里"，导出与校验互相打架。

### 16.3 关键：限制必须是**可执行的**，不能只是文档

三道，全部共用**同一个校验实现**（一份代码、三处调用）：

1. **部门本地**：编辑模板时（或在 CI/预览里）跑一次校验 → "第 3 个 fields 项的 `name` 与骨架字段冲突"、
   "用了不支持的校验器 `script`"——**发布前报错，而不是发布后**；
2. **agent 填卡前**：拿到模板先校验一次，模板本身不合法就**不要按它填**（否则会按错模板产出一堆脏数据）；
3. **服务端入库前**：`(template_id, template_version)` → 同一份校验器（这是事实边界，§10.1）。

### 16.4 一个容易漏的点：**契约本身要版本化**

`contract.json` 带 `contractVersion`。平台将来加字段或收紧限制时：
老模板仍按**它声明时的契约**解释，或在加载时提示"该模板基于 contract v1，当前 v2，请升级"。
没有这一步，平台一次收紧就会让所有部门的模板同时失效——**这个代价我们付不起**（部门会认为"你们又改了、我又得动"）。

### 十五之三、两层已接上并上线（2026-10-19）

用户口径：_"让 ucas-proxy 直接获取通讯录、UWork 从网关取"_ —— **这本来就是既有架构**
（`imHttpClient.directory()` → `GET /api/directory/users`，客户端从不直连企微；企微凭据只在 control-plane）。
这回补的是**没接上的两处**：

**① 目录端点暴露负责人标记**：`users.is_department_head` 列（`department/list` 的 `department_leader` 解析、

**② 白名单快照带部门负责人 + msgbus 路由第 4 层兜底**：`ImAllowlistSnapshot.leaders`（可选字段，

### 十四之三、负责人读本部门正文 + 三处修复（2026-10-19 收尾）

用户口径：_"应该是直接允许负责人拉取自己部门的正文，方便自己本地汇总和分析。"_

**已落地（生产实测）**：可见性加一条「作者 | 收件人 | **本部门负责人**」（判定用快照的 `leaders`：
`isDepartmentHeadOf(userId, department)`，与审核人路由同一份数据，**不另建"经理"概念**）；
`GET /api/work-items?filter[department]=X` 只在"查看者确实是 X 部门负责人（或 org_admin）"时放开，否则 403。
实测：吴鹏（测试部负责人）→ `scope: department`、4 条、**含别人的记录与完整正文**；
辛晓华（非该部门负责人）→ 403 `department rollup requires being that department head`；
吴鹏越部门（研发管理部）→ 403。

**同批修掉的三件**：

1. **`filter[...]` 从来没生效过（整条查询机制静默失效）**：Express 默认 query parser 把
   `filter[type]=x` 解析成**嵌套对象** `{filter:{type:'x'}}`，而代码按字面键 `'filter[type]'` 读 → 过滤条件被忽略，
   返回的永远是"与我相关"的默认列表。**之前几次 curl 没发现，是因为当时的数据恰好全符合条件**。
   修法：`queryValue()` 两种形态都认（嵌套对象 + 方括号被 `%5B/%5D` 转义后的字面键）；`page[size]`/`page[cursor]` 同理。
   **教训：路由层的行为只有真发 HTTP 才验得到**——store 单测全绿也拦不住这种 bug。
2. **`body` 当正文渲染的一整类泄漏**（用户报"发送方显示 json"）：agent 侧是提交脚本打印 JSON（已改人话输出 +
   脚本自己把审核人 id 解析成人名 + SKILL.md 禁止往对话里贴 JSON）；客户端侧是**六处**直接渲染 `body`
   （收藏列表、置顶面板、检索命中、引用块、转发预览、复制）→ 收口成一个 `messageBodyText()`（新载荷只加一处分支）。
3. **面板三档阈值改为按内容需求算**：三栏舒适需 rail 56 + 列表 240 + 消息列 ≥560 ≈ 856，所以
   `<720` 折叠成浮层、`720–879` 停靠窄列、`≥880` 舒适（实测用户拖到的 656px 现在会折叠）。判定与形态两个纯函数 + 6 条单测。

### 十四之四、审核动作闭环：卡片上的「已阅/退回」真能执行（2026-10-19）

通用机制见 `specs/messaging-and-channels.md` §12.18。这里只写工作项这一侧的具体映射：

- **卡片动作 → 端点**：`action.id === 'review'` → `POST /api/work-items/:id/review {status:'reviewed'}`；
  `action.id === 'return'` → 同一个端点 `{status:'returned', comment}`，**comment 必填**（服务端已强校验，
  客户端在提交前用弹窗收集，空意见不允许提交）。
- **谁有权点**：审核人（`recipient_ids` 里且不是作者本人）。**只由服务端判**——客户端把 403 原文显示出来
  （"不是审核人"），不做按钮级预判。第 1 层规则解析结果落进 `recipient_ids` 之后，"谁能点"与"谁能看"是同一份数据。
- **执行后**：服务端改写**审核人那张卡片**的正文——去掉 `review`/`return` 两个动作，加一条
  「已审核 / 已退回 · 时间 · 意见」的结论段与徽标；作者照旧收到独立的回执卡片（`buildReviewCard`）。
- **找那张卡片**：不新增投递台账，按"作者↔审核人的 DM 里的卡片消息（正文含 `work-items.item:<id>`）"查。
  这样**存量卡片**（本次之前投出去的）也能被改写，不需要数据迁移。
- **系统写入**：改写的是**别人发的**消息（卡片由作者身份投递），所以走一条明确的系统写入口
  （`replaceMessageBodyAsSystem`），不复用"只有发送者能改"的用户编辑路径。

**验收场景与实测（2026-10-19，生产 msgbus + dev 客户端全过）**：

1. 点「已阅」→ 记录 `status=reviewed` + `reviewedBy/reviewedAt` 落地；作者收到回执卡片；
   审核人那张卡片 2.5s 内收尾（按钮只剩「查看详情」、徽标「已阅」、结论段带时间）✓
2. 点「退回」→ 弹窗必填意见（空意见被拦且弹窗不关）→ 记录 `returned` + `reviewComment`；
   作者收到带「退回意见」的回执；审核人卡片徽标「已退回」并带意见 ✓
3. 非审核人点 → 服务端 403、客户端显示错误原文、记录不变（服务端 403 与客户端展示各有单测）✓
4. 刷新/换设备后按钮不复活（卡片已被服务端改写，不是靠本地状态）✓ —— 这条是"服务端改写卡片"这个设计的直接目的
5. **存量卡片也要能点**：`server` 动作带 `target` 是本次才加的，之前投出的卡片没有 target；
   客户端用"同卡片其它动作的 target"兜底，实测老卡片点「已阅」同样生效 ✓（真机上用户手点先撞到这条，才补的）
