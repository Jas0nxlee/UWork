# 测试部工作记录与汇报

这份技能只做一件事：**把散在 UWork 里的测试工作，整理成部门台账要求的样子，让人确认后提交出去。**
台账的形状不是这份技能定的——是 `schema.json` + `vocabulary.json`（部门自己的模板）定的，限制由
`../_platform/PLATFORM-CONTRACT.md` 规定。**技能负责"问对、写对、别漏"，模板负责"字段与取值"，服务端负责"事实边界"。**

## 一、先看模板，再看素材

1. 读 `schema.json`（要哪些字段、哪些必填、取值受什么约束）与 `vocabulary.json`（受控词表）；
2. 读 `../_platform/PLATFORM-CONTRACT.md` 的限制（**骨架字段不能改、不允许自定义校验器**）；
3. 不明白的字段**先问用户**，不要猜——猜错的字段会进台账，改起来比问一句贵得多。

## 二、素材从哪来（**不是只看当前会话**）

按这个顺序收集，缺哪块就问用户：

1. **本周/本月所有会话**：让宿主/工具给出"这段时间我做过哪些会话与任务"的清单（含标题、时间、产物路径），
   再用 `Read` 展开需要的会话内容。**不要只总结当前这一个会话**——那是"凭印象写"，不是汇报。
2. **工作区里的产物**：`工作输出物` 这一列要填的是**交付物名字**（文档/计划/报告），
   从工作区与会话产物里认（docx/xlsx/pptx/md 等），而不是编一个名字。
3. **用户给的文件**：他说"今天的记录""这个文件"，或者直接把文件拖进会话——把文件内容读进来，
   按台账字段归纳（**不要照抄全文**，要填成字段）。
4. **测试方式**：这条能自动判断就自动判断（在 UWork 里做的记为 `AI测试`），判断不了再问。

## 三、填写规则（写之前先看这几条）

- **骨架字段放顶层**（`projectId`/`projectName`/`managerId`/`engineerId`/`occurredAt`/`endedAt`/`periodKey`/
  `title`/`summary`/`content`/`problems`），**模板字段放 `fields`**（`测试方式`/`测试内容分类`/`工作输出物`…）。
  放错位置校验器会直接报"这是骨架字段……"。
- **`periodKey` 用 `YYYY-MM`**（月）——部门的台账是按月记的（同一个项目每月一行），不要按周填。
- **受控字段必须来自词表**（`测试内容分类`/`测试方式`/`项目状态`/`是否计入统计`）：
  只能从 `vocabulary.json` 里选；**没有合适的取值时问用户**，不要自己造一个（`99-我编的分类` 会被服务端拒）。
- **`problems` 要写"卡在哪、需要谁配合"**，不要写"一切顺利"——领导看这一栏就是想知道哪里需要他出手。
- **`工作输出物` 用文件名/文档名**，多个用顿号分隔；有实际文件时同时附上（`attachmentIds`）。
- 拿不准"算不算计入统计"就问；部门台账里 `是否计入统计=否` 的记录不进汇总口径。

## 四、流程（四步，绝不跳第三步）

1. **汇总 + 暂存**：按 §二收集素材 → 按 §三填成一份草稿 JSON → **立刻放进本地暂存箱**
   （平台通用件，见 `../_platform/LOCAL-DRAFTS.md`）：

   ```bash
   node skills/_platform/drafts.mjs stage --kind dept-qa-report.draft \
     --title "<记录标题>" --payload /tmp/qa-draft.json
   ```

   它会打印 `#<草稿编号>` 与位置。**草稿一写出来就入箱**——这就是"暂存"的全部含义，
   用户点不点卡片上的「暂存」都无所谓（那个按钮只表示"留着"）。之后任何时候用户问
   「我暂存的那份呢」，你都能用 `node skills/_platform/drafts.mjs list` 列出来（默认只列还没报出去的）。

2. **自查**（必做）：

   ```bash
   node skills/_platform/work-item-contract.mjs --template skills/dept-qa-report --payload /tmp/qa-draft.json
   ```

   有错就改到通过为止；**校验器报什么就改什么**，不要绕过它。

3. **给本人确认**：先生成卡片，让人**看**而不是读 JSON：

   ```bash
   node skills/dept-qa-report/scripts/render-card.mjs --draft /tmp/qa-draft.json --draft-id <草稿编号>
   ```

   它会输出两行：**文件路径** 和一行 `::visualize{"path":"…"}` 指令——**把那行指令原样贴进你的回复**
   （应用会把它渲染成对话里的卡片），再配一句话说明要点（做了什么 / 产出了什么 / 报给谁 / 哪个周期）。
   明确问："**这样报可以吗？要改哪里？**" —— 用户说"改"就改回去重走第 2 步。

   **下面两条错了，卡片就是"静默地不出现"**（脚本已经替你挡掉大部分坑，但贴的时候还会踩）：
   - **指令必须是正文纯文本**。放进 ``` 代码块、`行内代码`、`<pre>`里一律**不渲染**——应用把代码区里的`::visualize` 当示例，故意保持惰性。不要"为了排版好看"把它包进代码块。
   - **不要自己指定输出路径**：默认就落在应用能读取的可视化根目录（`ZCODE_GEN_UI_OUTPUT_ROOT`）里。
     换成 `/tmp`、工作区目录，或换成含大写/下划线/点开头的文件名，都会读不到。

   卡片底部有**「汇报」和「暂存」两个按钮，性质不一样**：
   - **「汇报」**＝让 agent 去提交。点它会给你发一条 `汇报：<标题>`（宿主会校验用户手势，没有手势时
     退化成一次确认弹窗——卡片脚本不可能自己触发你）。**收到 `汇报：…` 才走第 4 步提交**。
   - **「暂存」**＝**纯本地**，不给你发任何消息、不进会话、不打模型：卡片只在用户本机记一笔"暂存于何时"。
     草稿按第 1 步已经在暂存箱里了（卡片上那行就是它的位置）。**你不需要为暂存做任何事。**
   - 用户也可以**直接回一句话**：回「汇报…」走第 4 步；回「暂存…」只需确认它还在暂存箱
     （`drafts.mjs list` 看一眼），**不要上传、不要提交、不要重新生成记录**。

   三个动作都**不等于"已经提交"**——提交是你做的事（第 4 步），不是按钮做的。

4. **提交**：本人确认后再提交（**你没得到"确认"之前不许提交**）：

   ```bash
   node skills/dept-qa-report/scripts/submit-work-item.mjs --draft /tmp/qa-draft.json --draft-id <草稿编号>
   ```

   带上 `--draft-id` 时，提交成功后脚本会把暂存箱里那条标成"已报出"（`submitted` + 业务编号），
   于是 `drafts list` 里就只剩还没报出去的了。

   凭据由宿主注入（`UWORK_WORK_ITEM_BASE_URL` / `UWORK_WORK_ITEM_TOKEN`），**不要打印它们、不要在命令行里手传令牌**；
   缺这两个变量就说明宿主还没接上（照实告诉用户"能准备好草稿但发不出去"），不要绕。
   提交后按下面这种**人话**回一句（脚本已经这么打印了，直接引用即可）：

   ```
   ✓ 已提交：第 43 周实验记录与结论（2026-W43）
     审核人：吴鹏
     规则来源：按部门负责人兜底
     编号：c5843ca4-…
   ```

   **不要把 JSON、字段名清单、draft 文件内容贴进对话**——那是给我看的，用户要的是"报了没有、给了谁"。
   需要机器可读结果（排障、脚本）时加 `--json`，那是给命令行用的，不是给对话用的。
   脚本已经把审核人 id 解析成人名（它会去查一次通讯录），所以直接引用那段输出即可。
   返回里带 `resolvedReviewers` 与 `resolvedBy`（`record`/`project`/`department`/`wecom`/`ask`）时，
   如实说"已送 X 审核（规则来源：…）"——用户据此判断要不要改审核人。

## 五、周报/月报是"视图"，不是另一种记录

部门台账的粒度是 **一个项目在某个月的一行**（月），而不是"一周一份报告"。所以：

- 汇总多件事时，**每条记录各填一行**（同一个项目同一月份的多件事可以合成一行，把 `content` 写全）；
- 用户要"周报"时，输出的是**这一周的记录清单 + 一段总结**（视图），提交的仍是记录本体；
- **不要为了周报凭空造字段**（比如"本周心情"），模板里没有的字段一律不填。

## 五之二、导出（给经理的那张表）

要把某段时间的记录导成 xlsx（**表头与列顺序来自 `export.columns.json`**，就是部门现有那张表的样子）：

```bash
node skills/dept-qa-report/scripts/export-ledger.mjs --period 2026-10 --out 台账-2026-10.xlsx
```

离线核对时可以用 `--from <items.json>` 喂一份已有数据（不联网）。

## 五之三、部门汇总（负责人 / 管理员才拉得动）

用户问「汇总一下本部门这个月的记录」「部门台账导一份」时，**顺序不能反**：

1. **先问清权限**（不要猜自己是谁）：

   ```bash
   node skills/dept-qa-report/scripts/rollup-scope.mjs
   ```

   它输出人话，例如「你：测试与服务保障部（部门负责人）／能按部门汇总：测试与服务保障部」。
   `canRollup` 为空就**如实说"只有负责人能汇总整个部门，你现在的权限只能看与你相关的记录"**——
   **绝对不要**把"拉不到"说成"这个月没有记录"（那是假消息，负责人会据此做错判断）。

2. **按部门拉取**（`--department` 用第 1 步给出的名字，别自己拼）：

   ```bash
   node skills/dept-qa-report/scripts/export-ledger.mjs --department <部门> --period 2026-10 --out 部门台账-2026-10.xlsx
   ```

   返回 403 时脚本会说"你不是该部门的负责人（这是权限，不是没有数据）"，原样转述即可。

3. **汇总怎么讲**：按「人 / 项目 / 周期」分组给数量与要点（谁报了几条、哪些还等着处理、遇到的问题是
   什么），**不要把正文整段抄进对话**——用户要的是全貌，不是把台账读一遍；需要明细就导出 xlsx 给他。

## 五之四、催办：谁还没交，替部门催一句（定时任务会调它）

用户说「催一下没交的人」「看看谁还没交」时跑：

```bash
# 先看清楚（一条都不发）
node skills/dept-qa-report/scripts/remind-missing.mjs --dry-run
# 真催（默认本部门、当月；--only 只催指定的人，验证时用它）
node skills/dept-qa-report/scripts/remind-missing.mjs
```

三条口径：

- **只用标准会话 API 发消息**：催办是业务，发消息是渠道——IM 服务不需要知道"谁该交"。
- **幂等靠查会话历史**（那个人的 DM 里已有本周期的「【自动提醒】<周期>」就不再发），不另建台账。
- **不具备资格就别催**：不是该部门负责人（或管理员）时脚本会直接拒绝——**如实转述，不要绕过**。

**定时由 UWork 的「定时任务」(automation) 负责**：到点把一段 prompt 派给 agent（例如「跑
remind-missing.mjs，把催了谁用一句话告诉我」）。周期与时刻属于业务，所以它在上层；IM 只是渠道。

## 六、红线

- **不许编内容**：字段值必须有出处（会话、文件、用户口述）。没有出处就写"待补充"并问用户。
- **不许替用户点提交**：确认是用户的动作，你只负责准备好草稿。
- **不许改模板**：字段、词表、限制是部门的事（`schema.json`/`vocabulary.json`/契约），
  你觉得缺字段 → 告诉用户"建议部门加一个 X 字段"，而不是自己加。
- **不许把整篇文档塞进 `content`**：字段有长度上限（见契约），长文应作为附件。
